## 2. 真实样例校准事实（动手前必须背下来）

| 项 | 微信 xlsx | 支付宝 csv |
|----|-----------|-----------|
| 总行数（含前言） | 707 | 693 |
| 前言 / 表头 | 前言 17 行（第 6、16 行整行缺失）→ 表头第 **18** 行 | 前言 23 行 → 表头第 **24** 行 |
| 数据行 | **689**（707 − 18） | **669**（693 − 23 − 1） |
| 编码 | xlsx 内部 UTF-8 | **GB18030**（UTF-8 严格解码失败） |
| 列数 | 11 | **13（末列空，行尾多逗号）** |
| 时间类型 | `datetime` 或 `float`（序列号）**两种都有** | 全 `str`，`2026-10-21 09:42:31` |
| 金额类型 | 数值（`int` 461 / `float` 228，如 `8.8`） | 字符串 `"45.90"` |
| direction 分布 | 支出 613 / 收入 72 / `/` 4 | 支出 512 / 不计收支 155 / 收入 2 |
| 月分布 | 06:172 / 07:114 / 08:153 / 09:142 / 10:**108** | 06:**101** / 07:**136** / 08:**182** / 09:**143** / 10:**107** |

**三个必须记住的坑**：

1. **不能按固定行号取表头** —— 两个平台一个 18 行、一个 24 行，同平台换导出版本还会变。必须打分探测（§8.3）。
2. **金额禁止 `float * 100`** —— `8.8 * 100 = 880.0000000000001`，`int()` 后变 879。必须 `Decimal(str(v))` → `quantize` → `int`。
3. **微信的"707 vs 705"不是缺行** —— XML 少了第 6、16 行，都在前言区；数据区缺失为 0。若在数据区出现空行，必须计入 `parse_meta.empty_rows_skipped` 并在报告页提示，**不得静默丢弃**。

## 4. 关键实现要点

### 4.1 解析内核的 5 个纯函数（全部无 IO，便于 TDD）

```python
# 1) 编码：BOM → utf-8 严格 → gb18030 严格 → chardet(>0.7, 白名单) → E1002
detect_and_decode(raw: bytes) -> tuple[str, str]

# 2) 表头：对前 60 行打分，分母固定 15
#    score = (命中核心 × 2 + 命中次要 × 1) / 15
#    matched_core < 5 → 不作为自动候选（EX-03 走手动映射）
score_headers(source: RowSource, max_scan=60) -> list[HeaderMatch]

# 3) 文本：NFKC → 去 BOM/零宽/Tab → 折叠空白 → 去尾冒号 → empty_markers 归一为 None
clean_text(v, empty_markers=("", "/", "-", "—", "N/A")) -> str | None

# 4) 金额：Decimal(str(v)) → 取绝对值 → quantize(0.01, HALF_UP) → int(*100)
parse_amount_to_cents(v) -> int     # 失败抛 AmountParseError（行级 issue，不阻断批次）

# 5) 时间：datetime / float(Excel 序列号) / int / str 四路分派 → 秒级截断 → ISO 本地时间
parse_time_to_iso(v) -> str         # 失败抛 TimeParseError（行级 issue）
```

**Excel 序列号换算**（避免手写魔法数）：

```python
# 46316.82503472222 → 2026-10-21T19:48:03
# 用 1899-12-30 为基准（覆盖 Excel 的 1900 闰年 bug）
dt = datetime(1899, 12, 30) + timedelta(days=serial)
```

> `datetime(1899,12,30) + timedelta(days=46316.82503472222)` 的结果必须与样例的 `datetime` 分支**逐秒一致**（U-TM-01）。先写这条断言，再写实现。

### 4.2 表头探测的两个反直觉点

| 点 | 做法 | 原因 |
|----|------|------|
| 分母固定 15 | `(core×2 + secondary×1) / 15` | 若用"命中/该行非空列数"，只有 5 列且全中的行会拿满分，与 11 列全中并列，误选风险高 |
| 要求 5 核心全中 | `matched_core < 5` 直接丢弃 | 前言里的"交易时间：2026-06-01"这类文本可能虚构命中 1~2 个字段，全中要求可排除 |

同分时取**行号最小者**（先出现者胜）。

### 4.3 指纹构造（去重的唯一依据）

五项拼接：`channel | occurred_at | amount_cents | direction | normalized_counterparty`。

- 任一缺失（时间为 None 或金额解析失败）→ `fp = None`，该行标 `pending_manual`，**不参与自动去重**（EX-21）。
- `counterparty` 先去空白、去 `(*)` 掩码、小写化；`None` 与 `""` 视为同一。
- 用 `sha256` 前 32 位十六进制即可（本地单用户，无碰撞压力；文件内实测碰撞 0）。

### 4.4 流式落盘（EX-17 的正确姿势）

```python
CHUNK = 1 << 20
written = 0
with open(tmp_path, "wb") as f:
    while chunk := await upload.read(CHUNK):
        written += len(chunk)
        if written > MAX_FILE_BYTES:          # 5MB
            raise EntryValidationError(E1005)
        f.write(chunk)
```

- **先写临时文件再 `os.replace`**：中途失败不留半个文件，孤儿扫描才不会误报。
- 写前查余量：`shutil.disk_usage(buffer_dir).free < 200MB` → `E4001`（507），并清理本次临时文件。
- 落盘成功后**立即**插入 `staging_batch`（`status='uploaded'`），再触发解析；顺序颠倒会出现"文件在、批次不在"的孤儿。

### 4.5 批次状态机的本周期部分

本周期只允许三条流转（其余在 C3 补齐）：

```
uploaded ──parse成功──> mapped_pending
uploaded ──parse失败──> failed        （可重试：failed --parse--> mapped_pending/failed）
mapped_pending --mapping成功--> mapped_pending（计数更新，状态不变）
mapped_pending --precheck--> prechecked
uploaded/mapped_pending/prechecked --discard--> discarded
```

非法流转一律 `BusinessRuleError(E2002)`，用**表驱动**实现：

```python
ALLOWED = {
    ("uploaded", "parse"): {"mapped_pending", "failed"},
    ("failed", "parse"): {"mapped_pending", "failed"},
    ("mapped_pending", "map"): {"mapped_pending"},
    ("mapped_pending", "precheck"): {"prechecked"},
    ...
}
```

> 用 7×6 全矩阵参数化测试（U-BG-01），不要靠 if-else 手写。

### 4.6 预检的"零写入"如何自证

预检只做两件事：查指纹、组装 DTO。测试写法：

```python
before = (count("transaction"), count("raw_2026_06"), ...)
client.post(f"/api/v1/staging/batches/{bid}/precheck")
after = (count("transaction"), count("raw_2026_06"), ...)
assert before == after          # I-PC-01
```

同时断言 `staging_batch` 的 `new_count/dup_count/pending_count` **可以**变化（这是预检结果缓存，不是数据写入），但 `total_rows` 不变。

### 4.7 模板冲突三策略（EX-20）

| `policy` | 行为 | 返回 |
|----------|------|------|
| `abort`（默认） | 不写，提示已有默认模板 | 409 `E2003` |
| `overwrite` | 旧 default 置 `is_default=0`，新记录 `is_default=1` | 200 `TemplateDTO` |
| `save_as` | 新记录 `is_default=0`，名称自动加后缀 `(2)` | 200 `TemplateDTO` |

约束：同一 `channel` 下 `is_default=1` 的记录**至多一条**，用同事务内的"先降级后插入"保证。

## 7. 风险与回退

| 风险 | 表现 | 处理 |
|------|------|------|
| 表头打分为 0 | 样例换了导出版本 | **不改适配器绕过**，只补 `ALIASES` 别名或调 `max_scan`；补一条新样例回归 |
| 金额差 1 分 | 用了 `float*100` | 全局搜索 `* 100`，只允许出现在 `parse_amount_to_cents` 内部且输入是 `Decimal` |
| GB18030 误判为 UTF-8 | 严格解码"成功"但内容是乱码 | utf-8 严格解码只在无 `\ufffd` 且中文字符占比合理时接受；否则继续 gb18030 |
| 微信部分行时间为 `float` 且带时区 | 差 8 小时 | 明确不做 UTC 转换（I5），序列号按本地时间解释 |
| 大文件上传中断留下半文件 | 孤儿扫描报错 | 临时文件 + `os.replace`，中断只留 `.tmp`，扫描时忽略 `.tmp` |

**回退策略**：解析器是纯函数，回退成本低；但 `mapping_snapshot` 的字段一旦被 C3 依赖就不能改。因此 C2 收口时**先冻结 `MappingReq` 的字段名**，再进 C3。

## 8. 交接物

C3 开工前必须拿到：

1. `ParsedRow` 结构（`row_no, occurred_at, amount_cents, direction, counterparty, item, txn_type, payment_method, platform_category, platform_status, fp, raw_payload`）；
2. `ImportOrchestrator.replay(batch_id, mapping_snapshot) -> list[ParsedRow]` —— **C3 的入库与 C4 的重算都靠它重放**，签名必须稳定；
3. `staging_batch` 已含 `mapped_fields` / `parse_meta` / 计数字段；
4. 预检结果可被 C3 复用（`dedup_checker.check(rows)` 供入库二次去重，EX-22）。
