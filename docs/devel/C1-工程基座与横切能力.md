### 3.2 `Database` 三件事必须做对

```python
# 1) 连接级 PRAGMA —— 每个连接都要设，不能只在建库时设
conn.execute("PRAGMA journal_mode=WAL")        # 读写并发
conn.execute("PRAGMA synchronous=NORMAL")      # 写性能 vs 安全折中，SDD §5.3 写入预算的依据
conn.execute("PRAGMA foreign_keys=ON")
conn.execute("PRAGMA busy_timeout=5000")       # 与 DB_BUSY(E3003) 对应

# 2) 单连接 + RLock（ADR-11）—— 不引入连接池
# 3) row_factory = sqlite3.Row，让 Repository 用列名而非下标
```

> Windows 上 `WAL` 需要目录可写；`Database.close()` 必须显式 `wal_checkpoint(TRUNCATE)`，否则 `-wal`/`-shm` 残留会让"备份只拷一个 `.db`"失效 —— 这条直接支撑 C5 的备份设计。

### 3.3 `UnitOfWork` 的语义（后续所有事务的唯一入口）

```python
with uow.begin():          # BEGIN IMMEDIATE，立即取写锁
    ...                    # 业务
# 正常 → COMMIT；异常 → ROLLBACK 后原样抛出
# 嵌套 begin() 直接抛 RuntimeError（禁止隐式嵌套事务）
```

- `BEGIN IMMEDIATE` 而非默认的 `DEFERRED`：C3 的幂等闸门依赖"取锁即串行"，用 `DEFERRED` 会在 `UPDATE` 时才升级锁，出现 `SQLITE_BUSY` 概率上升。
- `UnitOfWork` 只暴露 `conn` 与 `begin()`；仓储由业务服务按需注入 `uow.conn`，不让 UoW 变成上帝对象（原计划写 `uow.staging` 占位，实施时放弃 —— 见 §9）。

### 3.4 `SchemaMigrator` 的 checksum 语义

| 场景 | 行为 | 退出码 |
|------|------|--------|
| 全新建库 | 执行 V001 → 写 `schema_version(1, now, sha256)` | 0 |
| 已是最新版本 | 跳过，日志 `schema up-to-date` | 0 |
| V001 内容被改（checksum 不匹配） | **拒绝启动**，提示"迁移文件被修改，请从备份恢复或新增 V002" | 4 |
| SQL 执行中途失败 | 单事务 ROLLBACK，库保持旧版本 | 4 |

> 为什么不允许改 V001：已发布版本的库无法重放，改 DDL 只能新增 `V002__xxx.sql`。这条规则在 C3 加 `raw` 分表、C5 加 `backup` 字段时都会被用到。

### 3.5 `path_guard` 与退出码 2 的联动

`validate_data_dir` 必须**先校验后创建**：路径非法时不能留下半成品目录。校验顺序按"便宜到昂贵"：

1. 非空/类型 → 2. 绝对路径 → 3. 长度 ≤180 → 4. 磁盘根 → 5. UNC/网络盘 → 6. 系统敏感目录 → 7. 安装目录内（`site-packages`/`node_modules`/`.git`）→ 8. `resolve()` 后重跑 4~7（防 symlink 逃逸）→ 9. 可写探测（写 `.probe` 再删）。

任一失败 → `InvalidDataDir(reason)`，`main.py` 捕获后打印：

```
数据目录不可用：<原因>，请修改 app.toml 的 data_dir
```
并以退出码 **2** 退出（SDD §2.3 表格）。

### 3.6 日志与脱敏

- 文件：`data/logs/app.log`，`RotatingFileHandler(maxBytes=10MB, backupCount=5)`，UTF-8。
- 格式：`%(asctime)s %(levelname)s %(name)s %(message)s`，时间用本地时间（与 I5 一致，不做 UTC）。
- 脱敏：`logger.Filter` 拦截 `counterparty`、`item`、`file_name` 的完整值，日志里只留前 2 字 + `***`。**日志里永不出现金额明细行**，只记聚合数。
- 事件日志（`event_log`）：C1 只留 `record(event, payload)` 接口与 `enabled=False` 的判定，真正落 `event_log` 表在 C5.4。

### 3.7 `lifespan` 六阶段（C1 就要按最终形态写）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    cfg = load_bootstrap_config()                 # 阶段 1 → 失败退出码 1
    paths = resolve_paths(cfg)                    # 阶段 2 → 失败退出码 2
    ensure_dirs(paths)                            # 阶段 3 → 失败退出码 3
    db = Database(paths.db_file)
    SchemaMigrator(db, MIGRATIONS_DIR).migrate()  # 阶段 4 → 失败退出码 4
    run_startup_reconciliation(db, paths)         # 阶段 5 → 失败仅告警，不退出（C3 实装，C1 空实现）
    lock = SingleInstanceLock(paths.data_dir)     # 阶段 6 → 失败/端口占用退出码 5
    ...
    yield
    db.close(); lock.release()
```

**顺序不可调**：单实例锁必须在建库之后取，否则两个进程会同时执行迁移。但端口占用检测必须在 `uvicorn.run` 之前完成（通过 `socket.bind` 试绑），否则 uvicorn 自己抛的异常无法映射到退出码 5。

## 6. 风险与回退

| 风险 | 表现 | 处理 |
|------|------|------|
| Windows 上 `RotatingFileHandler` 被占用导致轮转失败 | 日志停止增长 | 轮转前 `logging.shutdown()`，或改用按日期命名文件（`app-2026-10-22.log`） |

### 9.2 实施中发现的真实缺陷（已修 + 已加回归）

**现象**：`account-dashboard run` 启动即失败，日志 `StartupError: 已有实例在运行`，uvicorn 退出码 3。

**根因**：CLI 已完成 `startup()`（含抢文件锁），但未把状态挂到 `app.state._runtime`；`lifespan` 误判"未启动"，又执行了一次 `startup()`，第二次抢同一把锁必然失败。

**修复**：`cli._run` 显式 `app.state._runtime = state`；`lifespan` 增加双保险（`_runtime` 为空 **且** `database` 为空才自行启动）。

**回归**：`tests/integration/test_startup.py::test_lifespan_does_not_restart_when_state_injected` —— 把 `startup` 换成"一被调用就断言失败"的桩，确保永远不会重复启动。
