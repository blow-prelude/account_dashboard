## 2. 事务边界（照抄 SDD §7.5，不许改）

```
BEGIN IMMEDIATE
  ├─ UPDATE staging_batch SET status='ingesting', ingest_started_at=?
  │    WHERE id=? AND status='prechecked'          ← 幂等闸门，rowcount==0 → E2002
  ├─ replay(mapping_snapshot) → rows                ← 用快照重放，不重读用户当前映射
  ├─ 二次 find_by_fp(rows)                          ← 预检到入库之间可能有新数据（EX-22）
  ├─ CREATE TABLE IF NOT EXISTS raw_YYYY_MM × N     ← 按行覆盖的月份按需建
  ├─ INSERT INTO raw_YYYY_MM ...  (分批 executemany)
  ├─ INSERT INTO "transaction" ... (分批 executemany)
  └─ UPDATE staging_batch SET status='ingested', report_json=?, mapping_snapshot=?,
       committed_at=?, pending_delete_flag=1
COMMIT
  ↓（事务外，绝不能放在事务里）
DELETE 物理文件
  ├─ 成功 → UPDATE pending_delete_flag=0, deleted_at=?   （小事务）
  └─ 失败 → cleanup_service.enqueue(batch_id, path, E4003) → 返回 409 但数据已入库
```

**为什么闸门必须在事务内**：若先单独提交 `ingesting` 再开事务，进程崩溃会留下永久 `ingesting` 脏状态，需要额外自愈；放在同一事务里，`ingesting` 只存在于事务可见期内，崩溃时 SQLite 自动回滚，批次仍是 `prechecked` —— 天然满足 PRD 9.2「收口规则 4」。

**为什么删文件必须在事务外**：文件系统不在事务里，删了之后事务回滚会导致"数据没了文件也没了"。先提交再删，最坏结果是"数据在、文件也在"（可由启动对账补删）。

## 4. 关键实现要点

### 4.1 幂等不是"先查后改"

```python
# 反例（存在 TOCTOU，并发两次都查到 prechecked）
if repo.get(batch_id).status == "prechecked":
    repo.update_status(batch_id, "ingesting")

# 正例：条件 UPDATE + rowcount，靠 SQLite 写锁天然串行化
cur = conn.execute(
    "UPDATE staging_batch SET status='ingesting', ingest_started_at=? "
    "WHERE id=? AND status='prechecked'", (now, batch_id))
if cur.rowcount == 0:
    raise BusinessRuleError(ErrorCode.BATCH_STATE_CONFLICT, "该批次当前状态为已入库，无需重复提交")
```

`BatchGuard.try_enter_ingesting` 必须在**已开启**的 `BEGIN IMMEDIATE` 内调用（由 `IngestService` 负责开事务），守卫本身不开事务、不提交。

### 4.2 二次去重（EX-22 的真正含义）

预检是"快照"，入库是"当下"。两者之间用户可能：导入另一份重叠账单、手工修正过分类（不影响 fp）、撤销过 override。因此入库前必须**重新按 fp 查一次**：

```python
dups = transaction_repo.find_fp_in(conn, [r.fp for r in rows if r.fp])
accepted = [r for r in rows if r.fp not in dups or overridden(r.row_no)]
```

- `inserted = len(accepted)`、`skipped_dup = len(rows) - len(accepted)`；
- 报告页固定文案「以入库时实际执行结果为准」（EX-22），前端不得拿预检数字当结果。

### 4.3 `RawTableManager` 只增不改

```python
def ensure_table(conn, month: str) -> None:      # month="2026_06"
    conn.execute(RAW_TABLE_DDL.format(month=month))
    conn.execute(RAW_TIME_IDX.format(month=month))
    conn.execute(RAW_BATCH_IDX.format(month=month))

def write_rows(conn, month: str, rows) -> int:   # executemany，返回写入数
# 故意不提供 update_rows / delete_rows —— I7 靠"没有这个方法"强制，而非靠自觉
```

- 表名必须用正则校验 `^raw_\d{4}_\d{2}$` 后再拼 SQL（表名不能参数化，这是唯一的字符串拼接处，需注释标明）。
- `raw_payload` 存整行原貌 JSON：`json.dumps({列名: 原值}, ensure_ascii=False)`，**保留原始字符串**，不做单位换算（换算值另存 `amount_cents`）。
- 月份来源：`occurred_at[:7].replace("-", "_")`，不信任文件名。

### 4.4 报告四数字的口径

| 字段 | 定义 | 自洽性断言 |
|------|------|-----------|
| `total` | 本批次数据行数（= `parsed.rows` 长度，含被跳过的空行？**不含**） | `total == inserted + skipped_dup` |
| `inserted` | 实际写入 `transaction` 的行数 | 等于 raw 总写入行数 |
| `skipped_dup` | 因 fp 命中被跳过的行数 | — |
| `pending` | 写入行中 `status='pending'` 的数量 | 本周期 `pending == inserted`（C4 后才会小于） |
| `monthly` | `{"raw_2026_06": 101, ...}` | 各月之和 == `inserted` |

这四个数字是前端"导入报告页"的唯一数据源，**不可**用预检结果替代。

### 4.5 启动对账四步（顺序不可换）

| 步 | 动作 | 失败处理 |
|----|------|----------|
| ① | `UPDATE staging_batch SET status='prechecked', fail_reason='服务重启中断' WHERE status='ingesting'` | 失败仅告警（DB 不可用则服务本身已起不来） |
| ② | 查 `status='ingested' AND pending_delete_flag=1`，逐条删文件；成功清零，失败入队 | 单条失败继续下一条，累计报告 |
| ③ | 查"已入库 + flag=0 + 文件仍存在"（理论上不应出现）→ 记 WARN 并入队，**不自动删** | 人工确认 |
| ④ | 扫缓冲区孤儿（已知集合 = 未入库且未丢弃批次的 `stored_name`）→ 只报告 | 不自动删（EX-13 要求用户确认） |

对账**不阻塞启动**（SDD §2.3）：任何一个文件删不掉都只影响该文件，阻塞启动反而让用户进不去界面处理。

### 4.6 Windows 上的删除失败（必现问题）

`EX-11` 在 Windows 上极容易触发：openpyxl / csv 读取后文件句柄可能未及时释放。

```python
def delete_with_retry(path: Path, attempts=3, delay=0.1) -> bool:
    for i in range(attempts):
        try:
            path.unlink(); return True
        except PermissionError:
            gc.collect(); time.sleep(delay * (i + 1))
    return False
```

仍失败 → `cleanup_service.enqueue`，返回 409 `E4003`，文案「数据已入库，但原文件未能删除，已加入待清理」。**不能因为删不掉就回滚入库**。

### 4.7 追溯接口的返回形状

`GET /transactions/{id}/trace` 返回三块：

```json
{ "batch": {...BatchDTO}, "raw_record": {...RawRecordDTO}, "mapping_snapshot": {...} }
```

- `raw_record` 从 `raw_YYYY_MM` 按 `(batch_id, row_no)` 取，月份由 `transaction.occurred_at` 推出；
- `mapping_snapshot` 直接读 `staging_batch.mapping_snapshot`（I11 只写一次，全程只读）；
- 三者缺一 → `E2010` 并记录 WARN（说明数据分叉，属严重缺陷）。

## 7. 风险与回退

| 风险 | 表现 | 处理 |
|------|------|------|
| 事务内做文件 IO | 删文件耗时长，写锁被长期占用 | 代码评审硬规则：`ingest_service` 中 `unlink` 只允许出现在 `COMMIT` 之后 |
| 表名拼接被注入 | 月份参数含非法字符 | 正则白名单 `^raw_\d{4}_\d{2}$`，不通过直接抛 `RAW_TABLE_ERROR` |
| `pending_delete_flag` 语义漂移 | 有人用它表示"待删除主数据" | 列注释写死："仅表示缓冲区物理文件的删除意图"，DDL 层加注释 |
| 对账把用户文件误删 | 孤儿清单被"一键清理"误点 | 孤儿清理要求前端二次确认 + 后端文件名白名单校验（只允许删缓冲区目录内、且不在已知批次集合的文件） |
| 大批量 executemany 内存高 | 5 万行时爆内存 | 按 500 行分批，`rows` 用生成器而非 list（C2 已定的 `replay` 返回迭代器） |

**回退策略**：C3 一旦写入真实数据，`raw_*` 与 `transaction` 就不可逆。回退只能靠 C5 的备份能力 —— 因此 C3 开发期**必须使用临时 `data_dir`**（`tmp_path` fixture），禁止在真实数据目录上调试。

## 8. 交接物

C4 开工前必须拿到：

1. `transaction` 表已有真实数据（`status` 全为 `pending`，`category_*` 为 `NULL`）；
2. `transaction_repo` 具备：`find_fp_in`、`insert_many`、`iter_for_recalc(scope)`、`count_by(...)`、`sum_by_category(...)` 的**空壳签名**（C4 填实现）；
3. `mapping_snapshot` 可稳定重放（C4 重算依赖它得到与入库一致的 `ParsedRow`）；
4. 批次可 `ingested` 且 `report_json` 有值（C4 的"按批次重算"依赖批次状态）；
5. 4 条故障注入用例已进入 CI（C4/C5 每次提交都会跑，防止回归）。
