## 2. 分类引擎：三个"只有一处"

### 2.1 `direction` 只有一处判定

```python
def decide_direction(row: ParsedRow) -> Direction:
    # ① 渠道映射（§8.6）已给值 → 直接采用
    #    wechat: 支出→expense / 收入→income / "/"→neutral
    #    alipay: 支出→expense / 收入→income / 不计收支→neutral
    # ② 映射为 neutral，且 txn_type/item 命中「申赎/还款/互转/提现/转入/转出」→ 保持 neutral
    # ③ 映射缺失或未知 → neutral + issue=DIRECTION_UNKNOWN（该行仍入库，进待确认）
    return d
```

硬规则：

- **分类变更绝不写 `direction`**（I1）。`apply_manual` 的 SQL 只有 `category_l1/l2, status, updated_at` 四个字段。
- `neutral` 一律不计收支，与它被改成什么分类无关。测试用 U-ST-01 钉死：把一笔 neutral 改成「餐饮美食」，总支出不变。

### 2.2 规则评估只有一处

```python
def classify_all(rows):
    rules = rule_repo.list_enabled()          # 一次性快照，禁止逐行查库
    for row in rows:
        for rule in rules:                    # 已按 (priority DESC, created_at DESC) 排好
            if match(rule, row):              # match_field ∈ counterparty/item/txn_type
                yield draft(row, status="confirmed", l1=rule.l1, l2=rule.l2)
                break
        else:
            yield draft(row, status="pending", l1=None, l2=None,
                        hint_l1=..., hint_l2=...)   # hint 只来自 category_hint
```

- 排序在 SQL 里做（`ORDER BY priority DESC, created_at DESC`），Python 侧不再排 —— 否则"同级取最新"容易被稳定排序掩盖成"取最早"。
- `match_field` 三选一：`counterparty`（对方）、`item`（商品说明）、`txn_type`（交易类型）。匹配用"包含"（`keyword in field`），不是正则，避免用户输入特殊字符。
- 规则集为空时不报错，全部落 `pending`（这是合法状态）。

### 2.3 `hint` 只有一处来源

`hint_l1/hint_l2` 只能来自 `category_hint` 表（平台分类 → 建议分类，≈15 条种子），**永远不写 `category_l1/l2`**（ADR-10）。

> 支付宝的「交易分类」列只能进 `hint`，不能自动定分类。这是为了避免"平台分类把餐饮归到『日用百货』"这类错分被当成系统结论。

## 3. 重算：两入口一实现

### 3.1 作用域与语义

| 入口 | scope | 说明 |
|------|-------|------|
| FR-08（按批次重算） | `BATCH` | 只对 `ingested` 批次开放；未入库 → 422 `E2011` |
| FR-11（按规则重算） | `RULES` | 可传 `rule_ids`；不传 = 全部启用规则 |

| 目标行 `status` | 默认 | `overwrite_manual=True` |
|-----------------|------|------------------------|
| `pending` | 重算 | 重算 |
| `confirmed` | 重算 | 重算 |
| `corrected` | **跳过**，计入 `manual_kept` | 重算，并置回 `confirmed` |
| `excluded` | **跳过**，计入 `manual_kept` | 重算（二次确认文案必须明确"可能脱离已排除"） |

### 3.2 实现要点

```python
def recalculate(scope, *, batch_id=None, rule_ids=None, overwrite_manual=False):
    with uow.begin():                                   # BEGIN IMMEDIATE
        targets = transaction_repo.iter_for_recalc(scope, batch_id, rule_ids, overwrite_manual)
        rules = rule_repo.list_enabled() if not rule_ids else rule_repo.list_by_ids(rule_ids)
        for chunk in batched(targets, 500):
            rows = raw_repo.read_by_batch_row(chunk)    # 从 raw 取原始事实，不信任 transaction 的副本
            updates = [classify_one(r, rules) for r in rows]
            transaction_repo.bulk_update(updates)       # 只更新分类/状态变化的行
    # 失败 → ROLLBACK，报表数据与执行前逐字段一致（I-RC-02）
```

三条不可协商：

1. **重算不写 raw**（FR-08 规则 7）；raw 是事实，分类是解释。
2. **必须从 raw 重放**，不能用 `transaction` 现有字段反推 —— 否则"分类错了"和"事实错了"无法区分。
3. **单事务**，禁止分批提交。812 行实测 < 300ms，不需要为性能牺牲原子性。

### 3.3 `preview` 的文案责任

`preview` 返回 `{to_recalc, manual_kept, by_month}`，前端据此弹窗：

> 将重算 **812** 条，其中人工修正 **37** 条（不重算）。

`manual_kept` 必须准确，因为用户是靠这个数字决定要不要勾"覆盖人工修正"。少报 1 条就是欺骗。

## 4. 统计：唯一口径

### 4.1 `base_filter` 的唯一实现

```python
BASE_FILTER_SQL = (
    "occurred_at >= :start AND occurred_at < :end "
    "AND direction IN ('income','expense') "
    "AND status <> 'excluded'"
)

def base_filter(self) -> str:
    """任何统计 SQL 必须拼接此串，禁止手写过滤条件。"""
    return BASE_FILTER_SQL
```

三条硬性质（对应 I1/I2/I3）：

| 性质 | 保证 | 必须被测试捕获的反例 |
|------|------|----------------------|
| `neutral` 不进统计 | `direction IN (...)` | neutral 改分类后总支出变化 |
| `excluded` 不进统计 | `status <> 'excluded'` | 排除 100 元支出后总支出未减 10000 分 |
| `pending` **计入** | 不过滤 pending，聚合时 `CASE WHEN status='pending' THEN '未分类'` | 3 笔待确认时总额不含其金额，或「未分类」切片为 0 |

**CI 门禁**：`direction IN (` 这个字面量只允许出现在 `stats_service.py`。用 grep 断言，出现第二处即失败。

### 4.2 `PeriodResolver` 的边界

| kind | anchor | start | end（exclusive） | days | prev |
|------|--------|-------|------------------|------|------|
| month | `2026-10` | 2026-10-01 | 2026-11-01 | 31 | 2026-09 |
| quarter | `2026Q4` | 2026-10-01 | 2027-01-01 | 92 | 2026Q3 |
| year | `2026` | 2026-01-01 | 2027-01-01 | 365 | 2025 |

- `anchor=None` → 取今天所属周期；
- **半开区间**，`end` 恒为下一周期第一天 00:00:00（杜绝 `BETWEEN` 双计）；
- `days` 是**自然日数**，不是有流水的天数（日均分母，10.3）；
- 1 月的 `prev` 是上年 12 月；`last_year` 无数据 → DTO 字段 `None`，前端显示「—」而非 `0%`。

### 4.3 12 指标落点

| # | 指标 | 实现 | 空值语义 |
|---|------|------|----------|
| 1 | 总收入 | SQL `SUM(CASE WHEN direction='income' ...)` | 0 |
| 2 | 总支出 | SQL 同上 `expense` | 0 |
| 3 | 结余 | Python `income - expense` | 0 |
| 4 | 储蓄率 | `balance/income*100`；`income==0 → None` | 「—」 |
| 5 | 分类占比 | SQL GROUP BY + Python 再聚合一级 | `expense_total==0 → 0` |
| 6 | 环比 | `(cur-prev)/prev*100`；`prev==0 → None + flag='new'` | 「新增」 |
| 7 | 同比 | 同环比，基期 `last_year`；无数据 → None | 「—」 |
| 8 | 日均支出 | `expense/range.days`（分→元，2 位） | 0 |
| 9 | Top 5 商户 | SQL `GROUP BY counterparty ... LIMIT 5`（仅 expense） | `[]` |
| 10 | 待确认计数/金额 | SQL `WHERE status='pending'`（仍走 base_filter） | 0 |
| 11 | 未分类金额 | 同 10 的 expense 部分 | 0 |
| 12 | 趋势序列 | SQL 分桶；月内按日、季内按周、年内按月；空桶补 0 | `0` |

### 4.4 三入口同源（FR-19 的唯一验收方式）


## 9. 风险与回退

| 风险 | 表现 | 处理 |
|------|------|------|
| 统计口径分叉 | 出现第二处 `direction IN (` | CI grep 门禁 + 评审硬规则 |
| 重算与统计互相污染 | 重算中查统计得到中间态 | 重算全程 `BEGIN IMMEDIATE`，统计走读连接但被写锁阻塞；或前端在重算期间禁用报表刷新 |
| 规则集快照过期 | 重算用旧规则 | `recalculate` 在事务内重新加载规则，不用请求开始时的快照 |
| 分类停用后 `transaction` 仍引用 | 分类树出现幽灵节点 | `disable` 必须先迁移再置停用，同事务；`tree()` 对停用分类仍返回但标记 `enabled=false` |
| `hint` 被写成正式分类 | 平台分类污染结论 | `apply_manual` 与 `classify_all` 是唯一写 `category_*` 的地方，`hint_*` 单独列 |

**回退策略**：统计与重算都可回退（重算失败整体回滚；统计只读）。真正的不可逆点是"分类被大面积改错"，此时用 C5 的备份恢复，并在恢复后重跑 C4 的口径核对清单。
