## 二、背景与目标

### 2.1 背景

用户为在校大学生，收入来源全部为父母转账与学校奖助学金等拨款，无理财投资习惯，资金平时放在零钱通、余额宝中获取日收益。近期感觉生活开销偏大，产生记账需求，并希望为将来理财打基础。用户已将全部流水导出为电子表格，希望以此为数据源制作月度 / 季度 / 年度财务报表，并通过前端网页仪表盘查看各报表板块。

用户已明确的部署与数据要求：

1. **本地使用，前后端分离**：前端网页与后端服务分离，整体部署在本机；
2. **缓冲区导入**：账单原始文件先导入「缓冲区」，经预览、映射、去重预检、确认后正式入库；
3. **按月归档**：确认后的原始流水按月份存入对应的原始数据库（raw 按月分表）；
4. **删除原文件**：原始数据成功入库后，删除缓冲区中的原始文件，不在磁盘留存敏感副本。

### 2.2 要解决的问题

| 编号 | 问题 | 现状 | 期望 |
|------|------|------|------|
| P-01 | 钱花在哪里说不清 | 只有原始流水表格，无结构 | 分类汇总一眼可见 |
| P-02 | 手工统计麻烦 | 每月在 Excel 里筛选求和 | 导入后自动出报表 |
| P-03 | 缺少周期性复盘 | 无月度/季度/年度视角 | 三个周期报表一键切换 |
| P-04 | 收支口径混乱 | 零钱通/余额宝申赎、父母转账混在流水中 | 以 direction 为唯一准绳，明确 neutral 不计收支 |
| P-05 | 原始文件管理无序 | 导出文件散落磁盘、重复导入难防 | 缓冲区暂存 → 按月归档 → 入库后删除 |
| P-06 | 为理财做准备 | 只看到零散余额 | 先建立结余与储蓄率认知 |

### 2.3 成功指标与口径

| 编号 | 指标 | 目标值 | 口径 / 验证方式 |
|------|------|--------|----------------|
| M-01 | 分类正确率 | ≥ 95% | 上线后抽检 20 笔，与人工核对一致的比例 |
| M-02 | 月度复盘耗时 | ≤ 5 分钟/月 | 从打开工具到看完月报；现状手工估算 > 30 分钟（估算值） |
| M-03 | 使用连续性（**使用观察指标**，非产品验收标准） | 连续 4 周，每周导入 ≥ 1 次 | 观察用户使用习惯，不作为上线通过/失败判定；上线验证对应 13.3 第 1 条 |
| M-04 | 储蓄率可见 | 每月自动产出 | 储蓄率 = 结余 ÷ 总收入（口径见第十章） |
| M-05 | 原始文件零残留 | 入库后缓冲区原文件删除率 100% | 扫描缓冲区目录，已入库批次不得残留文件（含崩溃场景，由启动对账补删兜底，见 EX-16） |

### 2.4 关键假设（可推翻）

- A-01：账单为支付平台/银行导出的 **CSV 或 Excel 文本文件**，非 PDF、非截图。
- A-02：以**单机、单用户、单账本**使用为主；前后端分离指架构分层，服务仅监听本机回环地址。
- A-03：全部金额为人民币（CNY），本期不做多币种。
- A-04：月流水约 80–200 笔、三年累计约 3,000–8,000 笔（估算，用于容量设计）。
- A-05：示例数据（人名、金额）均为虚构脱敏，仅用于说明。
- A-06：用户能在本机完成 Python 运行环境与依赖的安装（一键启动脚本提供环境检查与引导，见 RK-15）。

## 三、名词与术语定义

| 术语 | 定义 |
|------|------|
| 流水 / 交易记录 | 一条收支明细，含时间、金额、方向、对方、商品说明等字段 |
| 收支方向（direction） | 收入（income）/ 支出（expense）/ 中性（neutral）。**是全部收支统计的唯一准绳**（见 10.3） |
| direction 判定规则（导入时） | 零钱通/余额宝申购赎回、信用卡还款、银行卡互转、提现 → neutral；父母转账、奖助学金等拨款 → income；转账给个人默认 neutral（可改分类，改分类不改变统计归属） |
| 资金流转 | **neutral 的默认分类标签与对外展示名**，指代零钱通/余额宝申赎、信用卡还款、银行卡互转、提现等资产形态转移。**不是统计开关**：是否计入收支只取决于 direction，与其分类归属无关 |
| 缓冲区（staging） | 原始文件上传后的暂存区：文件落盘于本地缓冲区目录，完成预览/映射/预检，经用户确认入库或丢弃 |
| 导入批次 | 一次文件上传产生的记录集合，贯穿缓冲区到入库的全生命周期 |
| 原始库（raw，按月分表） | 按月份分表存储的原始流水归档（raw_YYYY_MM），保留导入原貌，只增不改，是审计与重算的基础 |
| 主数据层（transaction） | 经清洗、分类、可修正的分析数据层，仪表盘与报表的数据源 |
| 一级 / 二级分类 | 分类体系两级结构，如「支出 → 餐饮美食」 |
| 分类规则 | 关键词 + 匹配字段 + 目标分类的自动映射规则，含优先级 |
| 去重指纹 | 交易时间（秒级）+ 金额（分）+ direction + 交易对方 + 商品说明 的组合键，用于重复导入识别；指纹字段缺失的记录不参与自动去重（见 EX-21） |
| 强制新增 | 对预检判定为「重复」的单条记录，经用户人工确认为真实消费后标记「强制新增」，入库时按新增处理并记录 override 原因留痕（见 P0-1 / FR-04） |
| 删除意图（待删除标记） | 入库事务提交前先行落库的「该缓冲区文件待删除」标记，使事务提交后、物理删除前的崩溃可通过对账补删（见 P0-3 / FR-06） |
| 启动对账 | 服务启动时执行的「已入库批次 ↔ 缓冲区文件」对账作业：已入库批次仍有文件的自动补删或列入待清理；同时扫描孤儿文件（见 EX-13/16/23） |
| 待确认 | 未命中任何分类规则、需人工处理的流水状态（主数据层 status=pending） |
| 储蓄率 | 结余 ÷ 总收入 × 100% |
| 环比 | （本期 − 上期）÷ 上期 × 100% |
| 同比 | （本期 − 去年同期）÷ 去年同期 × 100%；无去年同期数据显示「—」 |
| 前后端分离 | 前端 SPA 与后端 REST API 为独立两层进程，通过 HTTP/JSON 通信，本地部署，后端仅监听 127.0.0.1 |

## 四、需求范围

### 4.1 本期包含（In Scope）

**数据导入与归档**
- 文件上传至本地缓冲区（流式落盘并检测磁盘余量）、编码探测、解析预览
- 字段自动识别与手动映射（按来源渠道保存模板，含同渠道模板冲突规则）
- 去重预检（入库前标注新增/重复，只读；支持单条「强制新增」并留痕）
- 确认入库：事务内写入原始库（按月分表）+ 主数据层，成功后删除缓冲区原始文件（删除意图先落库 + 启动对账兜底）
- 缓冲区管理：批次列表、丢弃、重试、残留清理、目录缺失自检
- 原始库按月查看、按批次追溯、从原始库重算主数据层（与规则变更重算合并为单一重算服务，见 FR-08/FR-11）

**分类与分析**
- 自动分类（默认规则包 + 用户自定义规则）、手动/批量修正、重算
- 待确认队列集中处理
- 仪表盘：收支总览、分类占比、趋势、Top 商户
- 报表中心：月度 / 季度 / 年度报表，周期切换
- 流水明细：筛选、排序、单条编辑（仅分类/备注可编辑）

**数据管理**
- 备份与恢复：数据库文件整体备份 + 全量导出双通道（仅本机备份）
- 分类体系管理（增改启停一级/二级分类）
- 基础设置：单日支出阈值、备份提醒间隔、每周起始日、数据目录位置
- 帮助与说明：口径明示、备份指引、导入引导（FR-23）

### 4.2 本期不包含（Out of Scope，明确不做）

| 不做项 | 原因 | 去向 |
|--------|------|------|
| 自动同步银行 / 微信 / 支付宝数据 | 无面向个人的开放接口，且有授权与合规风险 | 后续版本池 |
| 理财收益记录、资产配置、投资建议 | 用户处于「先看清现状」阶段，避免范围蔓延（Q-02 已收口） | 后续版本池（5.3 v1.3） |
| 预算管理与超支提醒 | 依赖稳定分类数据，建议跑完一个账期后再做 | 后续版本池 |
| 多设备云同步 | 与隐私优先冲突，需单独方案 | 演进路径（见 5.3） |
| 引导备份拷贝至外部介质 / 网盘 | 委托方决策：仅本机备份，产品内不引导外部介质 | 不做；备份指引仅述本机保管 |
| 多用户 / 家庭账本 | 单用户场景不需要 | 不做 |
| 多币种、发票识别、短信解析 | 超出核心闭环 | 不做 |
| 对局域网/公网开放访问 | 个人财务数据，仅限本机回环地址 | 禁止 |

## 五、方案对比与选型说明

### 5.1 候选方案对比

| 维度 | 纯前端本地版 | 本地前后端分离（**选定**） | 云端方案 |
|------|--------------|--------------------------|----------|
| 架构 | 浏览器内解析 + IndexedDB | 前端 SPA + 本地 REST 服务 + 本地数据库 | 前端 + 云服务器 + 云数据库 |
| 数据位置 | 浏览器存储 | 本机服务端与数据库文件 | 云端 |
| 隐私安全 | 最好 | 好（数据仍在本机，需防误暴露） | 差 |
| 文件生命周期管理 | 弱（无法可靠落盘/删除服务端文件） | **强**（缓冲区落盘、事务入库、确认后删文件） | 强 |
| 大数据量处理 | 受浏览器内存限制 | 服务端流式处理，容量只受磁盘限制 | 强 |
| 断网可用 | 是 | 是（服务在本机） | 否 |
| 工程化与扩展性 | 差 | 好（API 可复用，为后续云同步留基础） | 好 |
| 部署成本 | 零 | 低（本地一键启动） | 高 |

### 5.2 推荐结论

**选定「本地部署 + 前后端分离」**。理由：

1. 满足用户明确的两项硬性诉求——前后端分离的工程结构；原始文件经缓冲区落盘、按月入库、确认后删除，这一文件生命周期管理依赖服务端能力，纯前端方案无法可靠实现；
2. 数据仍全部留在本机（服务仅监听 127.0.0.1），隐私风险可控；
3. 服务端处理导入与重算，前端专注展示，容量只受磁盘限制；
4. 为后续「可选加密云同步」演进保留 API 基础。

### 5.3 本期技术选型（已定）

> 定位：以下为**本期选定组合**（v1.1 中「技术栈为建议而非需求」的表述已废止）。分层与信任边界为技术栈中立的架构约束，见第八章 8.1。

| 决策点 | 本期选定 | 说明 |
|--------|----------|------|
| 前端 | React 18 + TypeScript + Vite；图表 ECharts；数据请求 TanStack Query；路由 React Router | 展示层只负责渲染与交互，不含统计计算 |
| 后端 | Python 3.11+ + FastAPI + Pydantic v2 + uvicorn | Pydantic 承担入口运行期类型检测与数据校验 |
| 数据库 | SQLite，Python 标准库 sqlite3，显式 `BEGIN IMMEDIATE` 事务控制 | 单文件零维护；参数化查询由驱动提供 |
| 文件解析 | openpyxl（.xlsx）、标准库 csv、chardet（编码探测） | 覆盖 UTF-8 / GBK / GB18030 |
| 文件上传 | python-multipart 流式落盘 | 落盘过程同步检测磁盘剩余空间（EX-17） |
| 接口契约 | 后端 Pydantic 模型为**单一事实源**；FastAPI 自动生成 **OpenAPI 3** 文档；前端 TypeScript 类型自 OpenAPI 生成（openapi-typescript）或按约定手工对齐 | 「类型检测」原则在后端由 Pydantic 运行期校验 + 类型注解承载，在前端由 TypeScript 编译期承载；契约变更流程见 8.1 第三小节 |
| 部署 | 一键启动脚本（含环境检查与依赖引导），后端仅绑定 127.0.0.1 | 见第十一章与 NFR |

**决策溯源**：架构师推荐 Node + TypeScript 全栈（共享 TS DTO + zod 契约），委托方在知悉理由后决策采用 Python + FastAPI。相应调整仅涉及契约机制（Pydantic + OpenAPI 取代共享 DTO + zod）与技术栈本体；**分层草案、信任边界、入口校验清单、统计单一来源等结论继续有效**（架构报告第十一节已确认其为技术栈中立）。

### 6.2 用户故事与验收标准

**US-01 导入账单至缓冲区**
作为学生用户，我想要把账单文件先导入缓冲区，以便预览确认后再正式入库。
- Given 已导出一份账单 CSV；When 上传文件；Then 文件落入本地缓冲区并展示解析预览（前 20 行），此阶段不写入原始库与主数据层。

**US-02 字段映射**
作为学生用户，我想要自动识别表头并能手动校正，以便兼容不同平台的导出格式。
- Given 一份标准格式微信 CSV；When 进入映射；Then 交易时间/金额/方向/对方/商品五个核心字段自动命中；Given 表头含自定义列，When 手动调整并确认，Then 按映射正确解析。

**US-03 去重预检**
作为学生用户，我想要入库前看到哪些记录是重复的，以便放心确认；误判时也能补救。
- Given 导入一份与历史部分重复的文件；When 完成预检；Then 预览中逐条标注「新增/重复」，并给出汇总（新增 N 条、重复 M 条）；
- Given 一条被标注「重复」但实际是真实消费；When 对其执行「强制新增」并说明原因；Then 该条按新增入库并留痕；
- 构造用例（客观断言）：① 同一对方同一天两笔同金额真实消费 → 均标注「新增」（若被判重，走「强制新增」补救）；② 跨月文件 → 按月拆分后标注正确、无错判；③ GBK 编码文件 → 解析无乱码且标注结果与 UTF-8 同名文件一致。

**US-04 确认入库与按月归档**
作为学生用户，我想要确认后流水按月份归档到原始库，以便追溯与重算。

**US-05 原始文件自动删除**
作为学生用户，想要入库成功后自动删除缓冲区里的原始文件，以便不在磁盘留存敏感副本。
- Given 批次已确认入库成功；When 入库事务提交并完成物理删除；Then 缓冲区中该原始文件被删除，扫描无残留（M-05）；
- Given 事务提交后、删除前进程崩溃；When 服务重启；Then 启动对账发现该残留并自动补删或列入待清理（EX-16）。

**US-06 自动分类**
作为学生用户，我想要导入后自动分类，以便不用逐笔手工整理。

**US-07 自定义规则与修正**
作为学生用户，想要为固定商户添加规则并修正误分类，以便报表越来越准。
- Given 待确认队列有 3 笔对方为「便利店」；When 批量设为「支出 → 购物消费」并勾选生成规则；Then 3 笔更新且后续同对方导入自动分类。

**US-08 查看月度报告**
作为学生用户，我想要查看月度财务报表，以便每月复盘一次。
- Given 本月已有入库流水；When 打开月度报表；Then 展示收支总览、分类占比、环比变化、Top 5 商户与文字摘要。

**US-09 周期报表切换**
作为学生用户，想要切换月度/季度/年度报表，以便从不同周期复盘。
- Given 库内有跨季度数据；When 切换报表周期；Then 各板块同步刷新，季度看环比、年度看同比（无上年数据时显示「—」）。

**US-10 导出备份**

## 七、功能需求

> 状态词约定：**必须（shall）/ 应该（should）/ 可以（may）/ 禁止（must not）**。每条需求有唯一编号，与 RTM（附录 A）对应。

### 7.1 导入与归档（缓冲区链路）

**FR-01 文件上传至缓冲区（Must）**
- 描述：用户上传账单文件，服务端将其写入本地缓冲区目录，生成导入批次，此阶段不写入任何业务表。
- 业务规则：
  1. 必须支持 CSV 与 Excel（.xlsx）；
  2. 单文件超过 5MB 或 50,000 行时必须提示分批；流式落盘过程中必须同步检测磁盘剩余空间，不足时报错并清理半成品文件（EX-17）；
  3. 文件必须落盘至本地缓冲区目录（非仅内存），刷新页面后批次不丢失；缓冲区目录可自定义（FR-22），路径须经合法化校验；
  4. 必须自动探测 UTF-8 / GBK / GB18030 编码；
  5. 上传过程必须展示进度，中断后可重试；
  6. 禁止将文件上传至任何外部服务。
- 验收标准：
  - Given 一份 5,000 行的微信账单 CSV；When 上传；Then 文件出现在缓冲区目录，页面展示解析预览（前 20 行）；
  - Given 上传过程中关闭页面；When 重新打开；Then 该批次仍在缓冲区列表中，可继续解析或丢弃。

**FR-02 缓冲区解析与预览（Must）**
- 描述：对缓冲区文件执行编码探测、表头识别与内容解析，输出预览。
- 业务规则：
  1. 必须展示：识别到的字段列表、前 20 行数据、总行数；
  2. 解析失败（编码异常/结构损坏）必须给出明确原因，批次置「失败」并记录 fail_reason，可「重新解析」或丢弃（见 9.2 状态机）；
  3. 禁止解析失败时产生任何数据库写入；
  4. 逐行金额/时间/方向解析失败**不阻断**整批，该行置「待确认」并标注原因（EX-06/07）。
- 验收标准：
  - Given 一份 GBK 编码文件；When 解析；Then 中文正常显示无乱码；
  - Given 一份结构损坏文件；When 解析；Then 提示具体错误原因，批次状态为「失败」，原始库与主数据层无变化。

**FR-03 字段映射（Must）**
- 描述：自动识别表头并允许用户校正，映射模板按来源渠道保存复用。
- 业务规则：
  1. 必须自动识别核心字段：交易时间、金额、收支方向、交易对方、商品说明；
  2. 次要字段（交易类型、支付方式）应自动识别，失败置空而非阻断；
  3. 必须支持手动调整映射，并按渠道（微信/支付宝/银行卡）保存模板；模板采用适配器结构，新增渠道不改主管道；
  4. 同渠道再次保存模板时的冲突规则：默认覆盖并二次确认（提供「另存为新模板」选项），见 EX-20；
  5. 禁止未确认映射即入库；五个核心字段未映射完成时阻断确认。
- 验收标准：
  - Given 标准微信 CSV；When 进入映射；Then 五个核心字段全部自动命中；
  - Given 手动映射后确认；Then 预览数据按新映射刷新；
  - Given 同渠道再次保存模板；When 确认覆盖；Then 该渠道后续导入使用新模板，旧模板可另存保留。

**FR-04 去重预检（Must）**
- 描述：入库前按去重指纹比对，逐条标注新增/重复，并提供误判补救入口。
- 业务规则：
  1. 必须按指纹（交易时间秒级 + 金额分 + direction + 对方 + 商品说明）比对库内记录；
  2. 预览中必须逐条标注「新增 / 重复」，并给出汇总计数；
  3. 同一天同金额不同对方的两笔，禁止误判为重复；
  4. **必须支持对单条「重复」执行「强制新增」**：用户确认其为真实消费后标记，须记录 override 原因与操作时间并留痕，入库时按新增处理（P0-1）；
  5. 指纹字段缺失（时间/金额解析失败）的记录**不参与自动去重**，置待确认并提示人工核对（EX-21）；
  6. 预检为只读操作，禁止此阶段写库；预检汇总为快照，最终以入库报告实际执行结果为准（EX-22）。
- 验收标准：
  - Given 与历史部分重复的文件；When 完成预检；Then 汇总显示「新增 N 条 / 重复 M 条」，构造用例（US-03）标注准确；
  - Given 同一天同金额不同对方两笔；When 预检；Then 均标注「新增」；
  - Given 对一条「重复」执行「强制新增」；When 确认入库；Then 该条写入 raw 与主数据层，批次报告记入新增，并在明细/报告中可查 override 记录。

**FR-05 确认入库与按月归档（Must）**
- 描述：用户确认后，在一个数据库事务内完成原始库按月写入与主数据层写入。
- 业务规则：
  1. 必须在一个事务内完成：①原始记录按交易月份写入对应 raw_YYYY_MM 表（保留导入原貌，含批次号与行号）②清洗分类后写入主数据层；
  2. 事务任何一步失败必须整体回滚，批次回「待确认」并保留 fail_reason 与重试入口（**不进入「失败」**，见 9.2 与 EX-10）；
  3. raw 表必须按交易时间所属自然月分表，无数据月份不建空表；跨月文件一次性入库时按月份拆分写入对应表，跨月任一分表写入失败即整体回滚；
  4. 入库完成后必须生成导入报告：总行数 / 新增入库 / 跳过重复 / 待确认；报告以入库时实际执行结果为准（EX-22）；
  5. 禁止部分成功状态（要么全成功，要么全回滚）；
  6. **必须为幂等操作**：批次状态非「待确认」（如已在「入库中」或「已入库」）时拒绝重复提交并提示当前状态（EX-18）；
  7. 全量重复时批次归宿为「已入库（新增 0 条）」，文件按 FR-06 删除，报告正常展示（EX-09）。
- 验收标准：
  - Given 覆盖 3 个月流水的文件；When 确认入库；Then raw_2026_01、raw_2026_02、raw_2026_03 三表按月份正确归入对应记录；
  - Given 模拟入库写入失败；When 事务回滚；Then 原始库与主数据层均无该批次数据，批次回「待确认」且原文件保留可重试；
  - Given 双击/多标签页重复提交；When 第二次提交；Then 仅一次事务成功，其余返回冲突提示。

**FR-06 原始文件清理（Must）**
- 描述：入库事务提交成功后，删除缓冲区中的原始文件；并保证崩溃场景下仍可清理。
- 业务规则：
  1. 必须严格遵循「先入库成功，后删除文件」的顺序；**删除意图必须先落库**（批次记录待删除标记）再执行物理删除（P0-3）；
  2. 删除失败时必须记入「待清理列表」并可重试，不影响已入库数据；
  3. 用户丢弃批次时，同样必须删除对应缓冲区文件；
  4. 删除动作必须记录日志（批次号、文件路径、时间、结果）；
  5. **必须承担启动对账职责**：服务启动时执行「已入库批次 ↔ 缓冲区文件」对账，已入库批次仍有文件的按已落库删除意图自动补删或列入待清理；同时扫描孤儿文件（EX-13/16/23）；
  6. 缓冲区目录被移动或删除时，启动时须检出并引导重建，无批次对应的存量数据不受影响（EX-23）。
- 验收标准：
  - Given 批次入库成功；When 事务提交；Then 缓冲区目录中该文件被删除，扫描无残留；
  - Given 删除时文件被占用导致失败；When 失败；Then 批次显示「文件待清理」，数据不受影响，提供重试入口；
  - Given 事务提交后、删除前模拟进程中断；When 服务重启；Then 启动对账检出残留并自动补删或列待清理（M2 故障注入用例）。

**FR-07 缓冲区管理（Must）**
- 描述：集中管理缓冲区批次与文件。
- 业务规则：
  1. 必须展示批次列表：文件名、渠道、状态、行数、上传时间、文件大小；
  2. 必须支持丢弃（二次确认，删文件）、失败重试；
  3. 应提供服务重启后的残留扫描：对无对应批次记录的孤儿文件提供一键清理；
  4. 缓冲区占用空间应展示，超过阈值（默认 500MB，可配）时提醒（should 级，可后移至 M3）；
  5. 缓冲区目录路径随数据目录设置变化，启动时须校验目录可读写。
- 验收标准：
  - Given 缓冲区有 3 个批次；When 打开缓冲区页；Then 列表状态正确（已上传/待映射/待确认/入库中/已入库/已丢弃/失败）；
  - Given 手动放入一个孤儿文件；When 点击残留扫描；Then 识别该文件并可一键清理。

**FR-08 原始库按月查看与重算（Must，P1-6 升级）**
- 描述：按月份查看原始归档、按批次追溯，并支持从原始库重算主数据层。重算与 FR-11「历史重算」合并为**单一重算服务**（委托方决策），同一事务与同一口径实现，提供「按批次」「按规则范围」两种触发入口。
- 业务规则：
  1. 必须按月份展示 raw_YYYY_MM 的记录（只读）；
  2. 必须按批次追溯：任一条主数据可回溯到来源批次与原始行；
  3. raw 数据禁止在主流程中修改；明细页仅分类/备注可编辑（见 FR-19），原始事实字段的更正通过重新导入正确文件解决，不做冲正机制；
  4. 重算执行前必须提示影响范围并二次确认，提示内容包含「将重算 N 条，其中人工修正 M 条（不重算）」；
  5. 重算默认**只处理未经人工修正/排除的记录**（status 为 corrected/excluded 的记录保持原分类），报告中单列「N 条人工修正未重算」；用户可显式选择覆盖人工处理结果（二次确认）；
  6. 重算为事务操作，失败整体回滚，禁止「半新半旧」中间态；
  7. 重算完成后必须给出变更条数；raw 表不变。
- 验收标准：
  - Given 点击 2026-03 的原始库；Then 展示该月全部原始记录（含原始字段原貌）；
  - Given 修改了分类规则后对某批次重算；Then 主数据层按新规则更新并给出变更条数，其中人工修正记录保持原分类，raw 表不变；
  - Given 重算过程中模拟失败；When 回滚；Then 主数据层保持重算前状态。

### 7.2 分类与分析

**FR-09 自动分类（Must）**
- 描述：入库时按默认规则包与用户规则自动分类，未命中进入待确认；同时按 direction 判定规则确定收支方向。
- 业务规则：
  1. 必须内置默认规则包：美团/饿了么/外卖 → 餐饮美食；滴滴/地铁/公交 → 交通出行；零钱通/余额宝/理财 → 资金流转；信用卡还款 → 资金流转；
  2. **必须按 direction 判定规则确定方向**：零钱通/余额宝申赎、信用卡还款、银行卡互转、提现 → neutral；父母转账、奖助学金等拨款 → income；转账给个人默认 neutral（见术语表与 9.5）；
  3. 必须支持用户规则：关键词 + 匹配字段（对方/商品/交易类型）+ 目标分类 + 优先级；
  4. 命中多条规则按优先级取高，同级取最新创建；
  5. 未命中必须进入「待确认」，报表中单列「未分类」；
  6. **统计口径以 direction 为唯一准绳**：direction=neutral 的记录禁止计入总收入/总支出，**与其分类归属无关**；用户修改分类不改变该记录的统计归属（P0-2）。
- 验收标准：
  - Given 对方为「美团外卖」的支出；When 入库；Then 归入「支出 → 餐饮美食」；
  - Given 一笔「零钱通-转入」；When 入库；Then direction=neutral、分类归入「资金流转」，不计入收支统计；
  - Given 用户把一笔 neutral 记录改分类为「餐饮美食」；When 查看月报；Then 该笔仍不计入总支出（口径以 direction 为准）。

**FR-10 手动/批量修正（Must）**
- 描述：在明细页与待确认队列修正分类，支持批量与规则生成。
- 业务规则：
  1. 必须支持单条修改分类；
  2. 应支持按对方名称批量套用（提示「将 XX 的 N 笔一并修改」，需确认）；
  3. 批量修正后应提供一键「生成规则」；
  4. 修正必须记录修改时间，可追溯；修正后记录状态置「已修正（corrected）」，重算默认不覆盖（见 FR-08 规则 5）。
- 验收标准：
  - Given 待确认队列 3 笔同对方「便利店」；When 批量设为购物消费并生成规则；Then 3 笔状态变为「已修正」，后续同对方自动分类。

**FR-11 分类规则管理（Must）**
- 描述：规则增删改查与启停，支持触发重算。
- 业务规则：
  1. 必须展示规则列表（关键词/字段/分类/优先级/启用状态）；
  2. 必须支持启停，停用后新导入不再套用；
  3. 必须提供重算入口，与 FR-08 为同一重算服务的「按规则范围」触发入口，规则集（影响范围提示、不覆盖人工修正/排除、事务失败整体回滚、执行前二次确认）与 FR-08 完全一致，两处互相引用、禁止两套实现；
  4. 规则与分类的保存须经入口校验（关键词非空、目标分类存在且启用、优先级为整数）。
- 验收标准：
  - Given 停用一条规则；When 重新导入含该关键词文件；Then 对应流水进入待确认；
  - Given 执行按规则范围重算并确认；Then 历史流水更新并展示「更新 N 条 / 人工修正 M 条未重算」。

**FR-12 待确认队列（Must）**
- 描述：集中展示未分类流水。
- 业务规则：必须按对方名称聚合便于批量处理；处理完成必须展示空态；报表页存在待确认时必须显著提示数量。**待确认（status=pending）记录计入收支总额**，在分类结构中单列「未分类」，口径见 10.3。
- 验收标准：
  - Given 10 笔待确认；When 全部处理；Then 队列空态，月报「未分类」金额归零；
  - Given 存在 3 笔待确认未处理；When 查看月报；Then 总支出包含这 3 笔金额，且分类结构中单列「未分类」。

### 7.3 仪表盘与报表

**FR-13 收支总览仪表盘（Must）**
- 描述：一页看到周期内收支全貌，支持周期切换。
- 业务规则：
  1. 必须提供 KPI 卡：总收入、总支出、结余、储蓄率及环比；
  2. 必须提供**简版**收支趋势图：按周期粒度（月内按日、季度按周/月、年度按月）的收支曲线，随周期自适应；**不含**异常高亮与收入到账标记（属 FR-15 增强项）；
  3. 必须提供分类支出占比图（环形图）；
  4. 应展示 Top 5 商户；
  5. 涨跌配色遵循国内习惯：不利变化（支出增加/结余减少）用红色，有利变化用绿色；
  6. 首屏应在 2 秒内（估算目标）渲染完成；所有统计数字**必须**来自后端统计服务，前端不得自行聚合（见 8.1）。
- 验收标准：
  - Given 本月有数据；When 打开仪表盘；Then 四张 KPI 卡与图表全部呈现；
  - Given 切换周期为「本季度」；Then 卡片与图表同步刷新为季度口径。

**FR-14 分类分析（Must）**
- 描述：按分类展示支出结构与变化，支持下钻。
- 业务规则：必须展示一级/二级分类金额、占比、环比；点击应下钻到明细；「未分类」必须单列。
- 验收标准：
  - Given 点击「餐饮美食」；Then 跳转明细页并带该分类筛选，汇总与报表一致。

**FR-15 趋势分析（Should）**
- 描述：在 FR-13 简版曲线基础上的**增强**能力：异常高亮与关键日期标记。
- 业务规则：应提供每日曲线与每周汇总两种粒度；单日支出超阈值（默认 300 元，可改）应高亮；收入到账日应显著标记。边界：FR-13 保证「有曲线」，FR-15 保证「曲线上的异常与标记」。
- 验收标准：
  - Given 某日支出 500 元超默认阈值；Then 该点高亮并悬浮提示；
  - Given 阈值改为 200 元；Then 超限判断按新阈值执行。

**FR-16 月度报表（Must）**
- 描述：月度财务报表，最高频使用。
- 内容：收支总览、分类结构表（金额/占比/环比）、Top 5 商户、日均支出、待确认提醒、自动文字摘要（3–5 条结论）。全部数字取后端统计服务，与 FR-13/FR-19 同口径。
- 验收标准：
  - Given 本月有完整数据；When 打开月报；Then 各板块汇总与明细页同口径核对一致；
  - Given 存在待确认；Then 报表顶部提示数量与处理入口。

**FR-17 季度报表（Must）**
- 描述：季度视角趋势与结构对比。
- 内容：季度内各月趋势对比、分类结构变化、季度结余与储蓄率、与上季度环比。
- 验收标准：Given 选择 Q2；Then 展示 4–6 月汇总与 Q1 环比。

**FR-18 年度报表（Must）**
- 描述：年度视角全年复盘。
- 内容：全年总览、12 个月收支对比、年度分类占比、年度储蓄率、同比（有上年数据时）。
- 验收标准：
  - Given 有两年数据；When 打开年报；Then 显示同比；仅一年时同比位显示「—」而非 0%。

**FR-19 流水明细查询（Must）**
- 描述：全量流水的表格化查询与编辑。
- 业务规则：
  1. 必须展示：时间、对方、商品说明、金额、方向、分类、支付方式、来源批次；
  2. 必须支持筛选：周期、分类、方向、支付方式、关键词、状态（含已排除/待确认）；
  3. 必须支持按时间/金额排序；
  4. 筛选汇总必须与仪表盘同口径一致；
  5. **可编辑字段仅限分类与备注**；交易时间、金额、方向、对方、商品说明等原始事实字段**只读**（raw 只增不改，主数据层不得与 raw 分叉）。原始事实录入错误的更正方式：重新导入正确文件并对错误批次/记录做排除处理，本期不做冲正机制；该规则与 FR-08 重算互相引用保持一致。
- 验收标准：
  - Given 筛选「餐饮 + 本月 + 支出」；Then 汇总金额等于月报餐饮分类金额；
  - Given 尝试编辑某条流水的金额；Then 该字段不可编辑，界面提示可通过重新导入更正。

### 7.4 数据管理

**FR-20 备份与恢复（Must）**
- 描述：数据备份与恢复，防止丢失。
- 业务规则：
  1. 必须支持数据库整体备份（SQLite 为文件拷贝；其他库为导出转储）；备份路径随数据目录设置（FR-22）；
  2. 必须支持全量 JSON/CSV 导出作为第二通道；
  3. 恢复时必须先预览将入库的记录数并校验备份文件有效性，二次确认后执行；**恢复执行前必须自动备份当前库**，恢复失败或中断可一键回退（EX-19）；
  4. 距上次备份超设定天数（默认 7 天，可配，见 FR-22）**必须**提醒；
  5. **备份文件仅存本机**，产品内必须明示「请用户自行妥善保管、勿上传公开平台」；产品内不引导外部介质拷贝（委托方决策）；EX-15 恢复引导不变。
- 验收标准：
  - Given 点击备份；Then 获得数据库备份文件并提示保管位置；
  - Given 恢复到空库；Then 条数与各周期汇总与原库一致；
  - Given 使用一个损坏备份执行恢复；When 恢复失败；Then 可一键回退到恢复前的库状态。

**FR-21 分类体系管理（Must）**
- 描述：维护一级/二级分类。
- 业务规则：必须内置预设体系（附录 B）；必须支持增改启停；停用已引用分类必须提示迁移（保留或迁到「其他」）；禁止无声删除被引用分类。分类归属不影响收支统计（统计以 direction 为准，见 10.3）。
- 验收标准：
  - Given 新增二级分类「咖啡」；Then 选择器立即可见；
  - Given 停用被 20 笔引用的分类并确认迁移；Then 迁移完成，收支总额不变。

**FR-22 基础设置（Must）**
- 描述：个性化偏好与运行环境设置（由 Should 升级为 Must：备份提醒间隔为 FR-20 的必须依赖，数据目录为委托方决策新增）。
- 业务规则：
  1. 必须支持单日支出阈值（默认 300 元）、**备份提醒间隔（默认 7 天，可配）**、每周起始日；
  2. 必须提供**数据目录位置**设置项（数据库文件 + 缓冲区目录的统一根目录，支持用户自定义）：路径必须为合法本地绝对路径，禁止指向系统敏感目录或网络位置，修改时须经入口路径合法化校验（M1 交付）；更换目录由 M5 数据迁移向导搬移数据库与缓冲区文件并更新启动配置；
  3. 仅 CNY，不做多币种；设置项键值须经类型校验（阈值 > 0、备份间隔 ≥ 1 天等）。
- 验收标准：
  - Given 阈值改为 200 元并保存；Then 趋势图与超限提示按新阈值生效；
  - Given 备份间隔改为 14 天；Then 提醒按新间隔触发；
  - Given 将数据目录修改为一个非法/敏感路径；When 保存；Then 拒绝并给出明确原因；
  - Given 通过迁移向导更换合法目录；Then 数据库与缓冲区文件搬移完成，服务重启后启动对账、备份路径均指向新目录。

**FR-23 帮助与说明（Must）**
- 描述：产品内静态说明页，承载口径明示承诺（9.5）与自助引导。
- 业务规则：
  1. 必须包含**资金流转与收支口径说明**：direction 为唯一准绳、neutral 不计收支、常见场景（申赎/信用卡还款/互转/提现/父母转账）的归属表，并说明「修改分类不改变统计归属」；
  2. 必须包含**备份指引**：如何备份、备份文件仅存本机、请妥善保管勿上传公开平台（不引导外部介质拷贝）；
  3. 必须包含**导入三步引导**：导出账单 → 上传缓冲区 → 映射与预检 → 确认入库；
  4. 应包含异常自助处理入口说明（编码失败另存为 UTF-8、待确认处理、文件待清理重试）；
  5. **内容不含理财相关内容**（与 4.2 / Q-02 收口一致）。
- 验收标准：
  - Given 打开帮助页；Then 口径说明、备份指引、导入引导三块内容可见且与实际行为一致；
  - Given 帮助页全量检查；Then 无理财/投资建议类内容。

### 8.1 架构设计原则与系统分层（需求侧约束）

> 定位：本节为**需求侧约束**，用于固化委托方提出的 5 条架构原则与边界，不写文件级实现细节。详细模块划分、目录结构、技术细节由架构方案承载。

**8.1.1 五条架构原则（逐条表述）**

| # | 原则 | 需求侧表述 |
|---|------|-----------|
| 1 | 前后端分离 | 同一台机器上的两个进程（前端页面服务 + 后端 REST 服务），通信仅经 HTTP/JSON，后端仅绑定 127.0.0.1；**前端不得直连数据库文件或缓冲区目录**，一切数据访问经后端 API；**展示层不含统计计算**（保证 FR-13/16/19 同口径，统计为后端单一计算源）。 |
| 2 | 分层设计，一层一类业务 | 系统分五层：**前端展示层**；后端**接口层 / 业务层 / 数据层 / 基础设施**。接口层只负责协议与入口校验；业务层承载全部领域逻辑（导入编排、分类、统计、备份）；数据层只负责持久化与事务；基础设施提供文件、编码、日志、启动作业等横切能力；展示层只负责渲染与交互。跨层依赖必须逐层经接口，**禁止接口层直连数据层（跳层）**；业务层内部模块间可经接口互相依赖。 |
| 3 | 模块之间依赖接口，需做类型检测、数据校验 | 模块间经定义良好的接口交互，接口须声明数据契约（字段类型、取值范围、必填性），契约变更可追溯。本期契约机制：**后端 Pydantic v2 模型为单一事实源**，承载入口运行期类型检测与数据校验；FastAPI 自动生成 OpenAPI 3 文档；前端 TypeScript 类型自 OpenAPI 生成（openapi-typescript）或按约定手工对齐，以提交前检查保证同步。即「类型检测」在后端由 Pydantic 运行期校验 + 类型注解承载，在前端由 TypeScript 编译期承载。 |
| 4 | 内部信任接口做的检测，不做重复防御 | **信任边界以进程为界**：前端 → 后端跨进程边界的输入（上传文件、接口参数）**一律视为不可信**，必须在系统入口一次性完成校验；后端内部模块之间信任已通过契约校验的数据，不做重复校验。数据访问层的参数化查询属数据库驱动职责，不构成应用层重复防御；业务不变量（状态机守卫、幂等、唯一性约束）由业务层在操作入口强制执行一次，**属业务逻辑而非重复防御**。 |
| 5 | 框架追求可拓展性和复用性 | 落地为四个具名扩展点：① 分类规则引擎（数据驱动：关键词 + 匹配字段 + 目标分类 + 优先级 + 启停）；② 渠道映射模板（适配器模式，新增渠道不改主管道）；③ 报表周期（月/季/年复用统一口径，新增周期不得复制统计逻辑）；④ 系统设置（键值 + 类型化读取）。REST 按资源化设计并为「可选加密云同步」预留复用基础。 |

**8.1.2 分层草案摘要（需求侧视图）**

| 层 | 承载业务 | 关键约束 |
|----|----------|----------|
| 展示层（前端） | 仪表盘、三期报表、流水明细、导入向导、缓冲区管理、原始库查看、规则管理、待确认队列、设置、帮助说明 | 只渲染与交互；不含统计聚合；不直连数据库与缓冲区目录 |
| 接口层（后端） | 路由、请求解析、**入口校验**、幂等控制、统一响应与错误码 | 不含业务逻辑与统计计算；禁止直连数据层 |
| 业务层（后端） | 导入编排、分类引擎、**统计服务（唯一口径源）**、备份恢复、去重预检、重算 | 承载全部领域逻辑与事务边界；不含展示决策 |
| 数据层（后端） | 实体仓储、raw 分表管理、事务控制、参数化查询（唯一 SQL 出口） | 不含业务规则 |
| 基础设施（后端） | 缓冲区文件管理、解析适配器与编码探测、本地日志、启动对账作业 | 不定义业务规则 |

**统计计算单一来源（与 P0-2 / P0-4 对应）**：`/stats/*`、`/reports/*`、`/transactions/summary` 三类 API 在接口层全部委托业务层统计服务的同一组计算函数（仅周期参数不同）；口径过滤（direction ∈ income/expense 且 status ≠ excluded，pending 计入并单列「未分类」）在统计服务内单一实现。接口层与展示层禁止任何统计聚合逻辑——这是 FR-13/FR-16/FR-19「同口径核对一致」的结构性保障。

**8.1.3 契约与校验策略摘要**

- **契约单一事实源**：后端 Pydantic 模型 + 由其生成的 OpenAPI 3 文档；契约变更流程 = 改 Pydantic 模型 → 重新生成 OpenAPI → 前端同步生成类型（或手工对齐）→ 记录契约变更；破坏性变更以 `contract:` 提交前缀标注。
- **统一约定**：响应统一封装 `{code, data, message}`；错误码集中枚举；金额一律整数分；时间一律 ISO 8601 本地时间字符串。
- **入口校验清单要点**（在系统入口一次性完成，失败即拒绝，不进入业务层）：

| 校验项 | 入口 | 规则要点 | 失败处理 |
|--------|------|----------|----------|
| 文件扩展名 / MIME | 上传 | 白名单 .csv/.xlsx，交叉验证 | 拒绝，EX-01 |
| 文件大小与磁盘空间 | 上传（流式落盘） | ≤ 5MB；同步检测剩余空间 | 拒绝并清理半成品，EX-17 |
| 数据行数 | 解析 | ≤ 50,000 行 | 提示分批，EX-05 |
| 编码 | 解析 | 探测 UTF-8/GBK/GB18030 | 批次可重试，EX-02 |
| 表头 / 结构 | 解析 | 表头可识别；空文件拒绝 | EX-03/EX-04 |
| 字段映射合法性 | 映射确认 | 五个核心字段必须映射；direction 值合法枚举；渠道模板归属合法 | 阻断确认，EX-20 |
| 金额 / 时间 / 方向（逐行） | 解析 | 金额清洗后转整数分；时间格式受支持；方向 ∈ {income, expense, neutral} | **不阻断**，该行置待确认，EX-06/07 |
| 指纹完整性 | 预检 | 指纹字段缺失不参与自动去重 | 提示人工核对，EX-21 |
| 确认入库（幂等） | 业务入口 | 批次状态必须为「待确认」 | 冲突提示，EX-18 |
| 丢弃批次 | 业务入口 | 状态允许流转 + 前端二次确认 | 冲突提示 |
| 恢复备份 | 业务入口 | 备份文件有效性预检 + 二次确认 + **恢复前自动备份当前库** | 阻断执行，EX-19 |
| 规则 / 分类管理 | 业务入口 | 关键词非空、目标分类存在且启用、优先级为整数 | 拒绝 |
| 系统设置 | 业务入口 | 键值类型校验（阈值 > 0、备份间隔 ≥ 1 天） | 拒绝 |
| 数据目录路径 | 设置入口 | 合法本地绝对路径；禁止指向系统敏感目录或网络位置 | 拒绝，FR-22 |

- **内部信任边界**：校验只发生在系统入口一次，后端模块之间传递已校验数据，不重复校验数据形状与取值；状态机守卫、幂等、唯一性等业务不变量在操作入口强制执行一次，属业务规则。

**8.1.4 可扩展设计点（需求侧）**

| 扩展点 | 扩展方式（不改主管道） |
|--------|------------------------|
| 分类规则引擎 | 新增规则 = 插一条规则数据；规则包以配置种子化 |
| 渠道映射模板 | 新增渠道 = 新增一个解析适配器 + 一条模板记录；样例文件就绪后补精确模板属数据级插入 |

| 系统设置 | 新增设置 = 新键 + 默认值 + 类型化读取 |
| REST 资源化 | 资源名词 + 统一动词 + 版本前缀，为演进路径 v1.2 云同步预留 |

## 九、业务流程与状态流转

### 9.1 文件生命周期（核心流程）

```
选择文件
  → 上传至缓冲区（流式落盘并检测磁盘余量，生成批次，状态=已上传）
  → 编码探测与解析预览（失败 → 状态=失败，记录 fail_reason，可重新解析/丢弃）
  → 字段映射（自动识别/手动校正/保存渠道模板，同渠道冲突默认覆盖+二次确认）
  → 去重预检（逐条标注 新增/重复，只读；可对单条「重复」标记「强制新增」并留痕；
              指纹字段缺失记录不参与去重，置待确认）
  → 用户决策 ──┬─→ 确认入库（幂等：仅「待确认」批次可提交）──→ 数据库事务：
  │              │       ① 原始流水按月份写入 raw_YYYY_MM（保留原貌 + 批次号 + 行号）
  │              │       ② 清洗分类后写入主数据层 transaction
  │              │       ③ 事务提交 → 先落库「待删除标记」→ 物理删除缓冲区原始文件
  │              │          （删除失败 → 记入待清理列表，可重试）
  │              │       ④ 生成导入报告（总/新增/跳过重复/待确认，以实际执行为准）
  │              └─→ 丢弃批次 ──→ 删除缓冲区文件 → 批次状态=已丢弃
服务启动 → 启动对账：已入库批次 ↔ 缓冲区文件（残留自动补删或列待清理）+ 孤儿文件扫描
```

导入报告固定展示四个数字：总行数 / 新增入库 / 跳过重复 / 待确认。预检汇总为快照，与报告不一致时**以入库报告为准**（EX-22）。

### 9.2 导入批次状态机（统一收口，单一事实源）

| 状态 | 说明 | 进入条件 | 允许操作 | 迁出 |
|------|------|----------|----------|------|
| 已上传 | 文件已落盘，未解析 | 上传成功 | 解析、丢弃 | 待映射 / 失败 / 已丢弃 |
| 待映射 | 解析成功，等待映射确认 | 解析成功 | 调整映射、确认映射、丢弃 | 待确认 / 失败 / 已丢弃 |
| 待确认 | 映射已确认且预检完成，已标注新增/重复 | 映射确认 | 确认入库、重新解析、丢弃 | 入库中 / 已丢弃 |
| 入库中 | 事务执行中（锁定） | 确认入库提交 | 等待 | 已入库 / 待确认（事务失败回滚） |
| 已入库 | 事务成功，原文件已删（或已落待删除标记待补删） | 事务提交 | 查看报告、查看跳过列表、按批次重算 | 终态 |
| 已丢弃 | 用户放弃，文件已删 | 用户丢弃并二次确认 | 重新上传 | 终态 |
| 失败 | **仅解析失败** | 编码/结构/IO 失败 | 重新解析、丢弃 | 待映射 / 已丢弃 |

收口规则：

1. **删除「待上传」状态**：批次在上传成功时才创建，「待上传」仅作为前端本地草稿态存在，**不落批次表**（10.2 status 枚举同步删除）；
2. **解析失败 → 「失败」**：记录 fail_reason，批次停留在缓冲区可重试；
3. **入库失败 → 回「待确认」**：事务整体回滚，保留 fail_reason 与重试入口，**不进入「失败」**（EX-10）；
4. **事务原子性**：「入库中」未提交的事务在进程重启时由数据库自动回滚，批次回「待确认」，不可能停留在「入库中」（EX-12）；解析中重启则停留在「已上传」；
5. 状态单向流转，**禁止从「已入库」回退**；丢弃必须二次确认；确认入库幂等（EX-18）。

### 9.3 原始库按月归档规则

- 按交易时间所属自然月分表：`raw_YYYY_MM`，如 2026 年 1 月流水写入 `raw_2026_01`；
- raw 表字段保留导入原貌（原始列 + batch_id + row_no + imported_at），**只增不改**；
- 无数据月份不建空表；跨月文件一次性入库时按月份拆分写入对应表，任一月份写入失败则整批回滚；
- 主数据层与 raw 通过 batch_id + row_no 关联，任一条分析数据可回溯到原始行；
- 批次表保存入库时的**字段映射快照（mapping_snapshot）**，保证重算与追溯可还原当时清洗口径。

### 9.4 主数据层状态机

| 状态 | 说明 | 迁移条件 | 统计口径（见 10.3） |
|------|------|----------|---------------------|
| 待确认 pending | 未命中分类规则 | 分类处理后 → confirmed/corrected | 计入收支总额，分类结构中单列「未分类」 |
| 已分类 confirmed | 自动规则命中 | 人工修正 → corrected；重算可覆盖 | 计入收支总额，按命中分类归集 |
| 已修正 corrected | 人工指定分类 | 可再次修正 | 计入收支总额；**重算默认不覆盖** |
| 已排除 excluded | 用户标记不计收支 | 可恢复 | **不进任何收支统计**，仅明细页可按状态筛选查看 |

### 9.5 收支口径与资金流转（口径核心）

1. **统计口径以 direction 为唯一准绳**：`direction=income/expense` 计入收支；`direction=neutral` 一律不计收支，**与其分类归属无关**。「资金流转」是 neutral 的**默认分类标签与对外展示名**，不是统计开关——用户把一笔 neutral 记录改分类到某个支出分类，该笔仍不计入总支出。
2. **direction 判定规则（导入时确定，可由用户在明细页调整方向）**：零钱通/余额宝申购赎回、信用卡还款、银行卡互转、提现 → neutral；父母转账、奖助学金等拨款 → income；转账给个人默认 neutral。
3. 该口径必须在产品「帮助/说明」中明示（FR-23），并在报表与明细中保持单一事实源（10.3）。

### 10.1 数据分层架构

| 层 | 载体 | 内容 | 写规则 |
|----|------|------|--------|
| 缓冲区 | 本地目录（文件）+ staging_batch 表 | 原始文件与批次元数据（含待删除标记、映射快照） | 上传写、确认/丢弃后删文件 |

### 10.2 核心实体与关键字段

**staging_batch（缓冲区批次）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string | 主键 |
| file_name / file_path / file_size | string / int | 缓冲区中的文件信息 |
| channel | enum | wechat / alipay / bank / other |
| status | enum | 已上传/待映射/待确认/入库中/已入库/已丢弃/失败（**无「待上传」**） |
| total_rows / new_count / dup_count / pending_count | int | 预检与入库统计 |
| mapping_snapshot | json | 入库时使用的字段映射快照（追溯与重算还原口径） |
| pending_delete_flag / deleted_at | bool / datetime | **删除意图标记**：入库提交前落库，物理删除后记录时间（P0-3） |
| fail_reason | string | 失败原因（可空，解析失败与入库失败均记录） |
| created_at / updated_at | datetime | 审计时间 |

**raw_YYYY_MM（原始库，按月分表）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | integer | 主键 |
| batch_id | string | 来源批次 |
| row_no | integer | 文件内行号 |
| occurred_at | datetime | 交易时间 |
| amount_cents | integer | 金额（分） |
| direction | enum | income / expense / neutral（统计唯一准绳） |
| counterparty / item / txn_type | string | 原始字段 |

### 10.3 指标口径定义（M4 启动前冻结，为全系统唯一口径源）

| 指标 | 计算口径 | 边界说明 |
|------|----------|----------|
| 统计基本过滤 | 周期内 **direction ∈ {income, expense} 且 status ≠ excluded** 的记录 | **唯一准绳是 direction**：neutral 一律不计收支，与其分类归属（含「资金流转」分类）无关；status=excluded 不进任何收支统计，仅明细页可按状态筛选查看 |
| 总收入 | 基本过滤下 direction=income 的金额之和 | 不含 neutral、不含 excluded |
| 总支出 | 基本过滤下 direction=expense 的金额之和 | 不含 neutral、不含 excluded |
| 待确认记录 | status=pending 的记录**计入**收支总额 | 在分类结构中单列「未分类」，金额计入总支出分母（FR-12/FR-14/FR-16） |
| 结余 | 总收入 − 总支出 | — |
| 储蓄率 | 结余 ÷ 总收入 × 100% | 总收入为 0 时显示「—」 |
| 分类占比 | 该分类金额 ÷ 总支出 × 100% | 「未分类」单列 |
| 环比 | （本期 − 上期）÷ 上期 × 100% | 上期为 0 显示「新增」 |
| 同比 | （本期 − 去年同期）÷ 去年同期 × 100% | 无去年同期数据显示「—」（FR-18） |
| 日均支出 | 总支出 ÷ 周期实际自然日天数 | 月按当月天数、季按季度天数、年按年天数；不按有流水的天数 |
| 报表与明细一致性 | 仪表盘 / 三期报表 / 明细筛选汇总全部取自后端统计服务同一组计算 | 展示层与接口层禁止自行聚合；预检汇总与入库报告不一致时**以入库实际执行结果为准**（EX-22） |

### 10.4 本地事件日志（可选，默认关闭）

本地可记录：导入成功率、待确认率、规则命中率、文件删除与补删次数、启动对账结果。**仅存本机，禁止上传**，设置中提供开关。

## 十一、权限与安全要求

1. 本期为单用户本机工具，不设账号体系；
2. 后端服务**仅绑定 127.0.0.1**，启动脚本与日志必须明示监听地址；禁止提供绑定 0.0.0.0 的选项，防止局域网暴露；
3. 缓冲区目录权限仅应用可读写；原始文件、数据库文件、备份文件均不得离开本机；数据目录可自定义但仅限本地合法路径，禁止指向系统敏感目录或网络位置（FR-22）；
4. 删除原始文件必须以「入库事务成功」为前提，顺序不可颠倒；删除意图先落库，崩溃场景由启动对账补删（FR-06）；
5. 前端输入一律视为不可信，必须在系统入口一次性完成校验；后端内部模块间不重复校验（见 8.1 原则 4）；
6. 禁止提供「自动抓取银行/支付平台数据」功能，避免授权与合规风险；账单来源限于用户自行导出文件，遵守各平台服务条款（个人备份自用）；
7. 备份文件为本地文件，产品内必须明示「**备份文件仅存本机，请用户自行妥善保管、勿上传公开平台**」；产品内不引导外部介质拷贝；
8. 文档与产品内出现的所有人名、账号、金额示例均为虚构脱敏数据。

| 编号 | 场景 | 触发条件 | 产品表现 | 恢复方式 |

| EX-10 | 入库事务失败 | 写入异常/磁盘满 | 事务整体回滚，批次回「待确认」并保留 fail_reason，原文件保留 | 重试或丢弃 |

| EX-17 | 上传时磁盘满/写文件失败 | 缓冲区目录写入报错 | 提示磁盘空间不足，批次标记失败并清理半成品文件 | 清理空间后重试 |

| EX-19 | 恢复备份失败 | 备份文件损坏、磁盘满、恢复中断电 | **恢复前自动备份当前库**；恢复失败提示并可一键回退到原库 | 重试恢复或回退 |
| EX-20 | 同渠道映射模板冲突 | 同渠道再次保存模板 | 提示冲突，默认覆盖并二次确认，提供「另存为新模板」 | 手动重新映射并保存 |
| EX-21 | 指纹字段缺失记录的去重 | 时间/金额解析失败置待确认 | 不参与自动去重，提示人工核对 | 重新导入正确文件后正常参与去重 |

### 13.3 上线后验证

1. 连续 4 周真实使用，每周导入 ≥ 1 次（**使用观察指标**，不作为通过/失败判定，见 M-03）；
