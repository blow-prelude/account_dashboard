## 一、评审结论摘要

1. **总体判断**：PRD v1.1 结构完整，背景→范围→方案→用户故事→FR→NFR→流程状态机→口径→异常→排期→风险→RTM 链路闭合，「缓冲区 → 预览映射预检 → 事务入库按月归档 → 删原文件」主链路自洽，部署形态与文件生命周期管理的前后对比（5.1）论证充分。文档主体可支撑架构评审。
2. **P0（4 条，必须改）**：均属口径与数据完整性问题，不修则报表数字与验收标准无法定义——
   - 去重指纹会误判「同秒同金额同对方同商品」的真实两笔消费，且误判后**无任何补救入口**（记录不入库、raw 只增不改，误判即静默丢失）；
   - 「资金流转」在术语、9.5、附录 B、FR-09 中同时以 **direction=neutral** 和 **一级分类** 两种身份出现，统计口径二义，直接影响总收入/总支出/储蓄率全部数字及 M-01 抽检标准；
   - 事务提交后、删文件前进程崩溃/断电时**无对账与补删机制**，M-05（原文件删除率 100%）与 13.3 验证第 5 条在该场景下必然失败；
   - 10.3 指标口径只按 direction 求和，未定义 status 维度，「已排除」记录是否计入收支、待确认记录如何计入，均无口径。
3. **P1（7 条，建议改）**：批次状态机三处不一致（待上传语义 / 入库失败归宿 / 解析失败归宿）；异常清单缺 6 类场景（含恢复备份失败、并发重复点击确认入库、上传磁盘满、映射模板渠道冲突等）；FR-19「单条编辑」可改字段范围未定义；FR-08 重算未定义与人工修正的关系；9.5 要求「帮助/说明中明示口径」但无功能承载；FR-08 标 Should 却列入 4.1 In Scope；13.2 依赖清单缺 2 项。
4. **P2（8 条，可选）**：多为口径细节、RTM 笔误、指标性质标注，不影响架构决策。
5. **对排期的影响评估**：全部 P0/P1 均为**文档级收口**，不涉及架构变更，不阻塞 M1 启动（Q-01 已具备 fallback 方案，见第四节）。需提示主理人：10.3 口径（含 P0-2/P0-4 修订）建议在 **M4 启动前冻结**，作为前后端「同口径」验收的唯一基准；M1 出口标准措辞建议弹性化以吸收样例延期风险。

## 二、问题清单

### 2.1 P0 必须改（4 条）

#### P0-1 去重指纹会误判真实重复消费，且误判后无补救入口

| 维度 | 内容 |
|------|------|
| 位置章节 | 7.1 FR-04、FR-05；9.1；12 章 EX-08；三章术语「去重指纹」 |
| 问题描述 | 指纹 = 交易时间（**秒级**）+ 金额（分）+ 收支方向 + 交易对方 + 商品说明。现实中「同一天同一秒、同金额、同对方、同商品说明」的两笔**真实**消费可能发生（便利店连续两次相同商品扣款、同一商户同时段两笔同额扣款、扣款重试产生的两笔真实扣款）。二者指纹完全一致，第二笔必被判重跳过；且被跳过的记录**不写入 raw 与主数据层**——FR-04 只允许标注「重复」，FR-05 只允许跳过，raw 只增不改且记录根本不在库中，事后**无法补救**。当前 PRD 无任何「强制标记为新增 / 补导入」入口。 |
| 影响 | 数据完整性受损且不可逆，金额越大越严重；直接违背 US-03「以便放心确认」的产品承诺；误判场景下用户对去重机制的信任崩塌。 |
| 修订建议 | 二选一或组合，写入 FR-04/FR-05 业务规则并补验收标准：① FR-04 支持对单条「重复」标注执行「强制新增」（记录 override 原因并留痕，入库时按新增处理）；② FR-05 导入报告的「跳过重复」列表提供「补导入该条」入口（独立事务补写 raw + 主数据层）。EX-08 同步补充该场景的产品表现与恢复方式。 |

#### P0-2 「资金流转」统计口径二义：direction=neutral 与一级分类两种身份混用

| 维度 | 内容 |
|------|------|
| 位置章节 | 三章术语表；9.5；10.2/10.3；附录 B；FR-09 规则 1/5 |
| 问题描述 | 术语表中「收支方向 = income/expense/neutral」「资金流转（不计收支）」是**方向语义**；附录 B 又把「资金流转（不计收支）」列为**一级分类**；9.5 说「默认为中性（资金流转）」；FR-09 说「归入资金流转，不计入收支统计」。后果：统计总收支时**以 direction 为准还是以分类为准没有定义**。若以分类为准——分类是用户可改的（FR-10/FR-21），用户把一笔资金流转改到「餐饮美食」后该笔即计入支出，口径随用户操作漂移；若以 direction 为准——若某平台导出将信用卡还款标为支出（direction=expense），规则又将其分类到「资金流转」，该笔计入总支出，违反 FR-09 规则 5「禁止把资金流转类默认计入支出统计」。 |
| 影响 | 总收入/总支出/结余/储蓄率/分类占比全部可能算错；M-01「分类与金额正确率」的抽检标准无法定义；FR-16/FR-19「报表与明细同口径」的验收缺乏唯一准绳。 |
| 修订建议 | 定稿明确**唯一口径**：「统计口径以 direction 为唯一准绳——direction=income/expense 计入收支；direction=neutral 一律不计收支，**与其分类归属无关**。『资金流转』是 neutral 的默认分类标签与对外展示名，不是统计开关」。配套修订：① 10.3 口径表增加该边界说明；② FR-09 规则 5 改为「direction=neutral 的记录禁止计入总收入/总支出」；③ 附录 B 将「资金流转」调整为「neutral 的默认分类标签」或保留分类名但注明统计以 direction 为准；④ 补充导入时 direction 判定规则（零钱通/余额宝申赎、信用卡还款、银行卡互转、提现 → neutral；父母转账/奖助学金 → income；转账给个人默认 neutral，可改分类后计入，即 9.5 现有规则）。 |

#### P0-3 事务提交后、删文件前崩溃/断电：无对账与补删机制，M-05 必然不可达

| 维度 | 内容 |
|------|------|
| 位置章节 | FR-06；9.1/9.2；EX-11/EX-12；M-05；13.3 验证第 5 条 |
| 问题描述 | 9.1 流程③为「事务提交成功 → 删除缓冲区原始文件」。若提交成功后、删除执行前进程被杀或断电：批次已入库、文件残留。FR-06「待清理列表」与 EX-11 只覆盖**运行时报错**（文件占用/权限）；若删除意图未持久化，重启后无任何记录表明该文件应删（EX-12 仅说「批次停留在中断前状态」，对「已提交未删」无定义）。该场景下 M-05 要求删除率 100%、13.3 要求扫描无残留，**指标与验收自相矛盾**。 |
| 影响 | 敏感文件残留，直接违背用户 2.1 第 4 条核心诉求；M-05/13.3 无法达成；残留文件再次导入时重复走预检，体验怪异。 |
| 修订建议 | 新增 EX 场景（建议编号 EX-16，见第三节）；需求级明确三点：① 删除意图须**先落库**（staging 记录待删除标记）再执行物理删除；② 服务启动时执行「已入库批次 ↔ 缓冲区文件」对账，发现已入库批次仍有文件的，自动补删或列入待清理列表；③ FR-06 规则补充启动对账职责，EX-11/12 与该场景的关系写清。 |

#### P0-4 10.3 指标口径未定义 status 维度：已排除/待确认记录是否计入收支无口径

| 维度 | 内容 |
|------|------|
| 位置章节 | 10.3 指标口径 vs 9.4 主数据层状态机（已排除）、FR-12、FR-21 |
| 问题描述 | 9.4 定义了「已排除（用户标记不计收支）」状态，但 10.3 总收入/总支出仅按 direction 求和，**未提 status**。若已排除记录仍计入支出，「标记不计收支」功能形同虚设；待确认（未命中规则）记录是否计入总额、在分类占比中如何呈现，也只有 FR-12「未分类单列」的间接表述，未进口径表，三处（仪表盘/报表/明细）实现时容易各算一套。 |
| 影响 | 结余/储蓄率/占比口径不完整；用户标记排除后报表数字不变会被当成 bug；FR-16/FR-19 的同口径验收缺乏依据。 |
| 修订建议 | 10.3 增加口径行：「总收入/总支出 = 周期内 direction 为 income/expense **且 status ≠ excluded** 的金额之和；待确认（status=pending）记录计入收支总额，在分类结构中单列『未分类』（金额计入总支出分母）；已排除记录不进任何收支统计，仅在明细页可按状态筛选查看」。FR-12/FR-21 相关表述改为引用口径表，确保单一事实源。 |

### 2.2 P1 建议改（7 条）

#### P1-1 批次状态机三处不一致：待上传语义、失败归宿、解析失败归宿

| 维度 | 内容 |
|------|------|
| 位置章节 | 9.2 状态机 vs FR-01/02/05 vs EX-10/12 vs 10.2 |
| 问题描述 | ① 「待上传」状态：FR-01 规定上传时即生成批次，则批次记录不存在于「待上传」之前，该状态永不出现在批次列表，10.2 status enum 却包含它；② 入库失败归宿：FR-05 规则 2 与 EX-10 说回「待确认」，9.2 状态机的「失败」却说明为「解析或入库失败，可重试」——同一失败两个归宿；③ 解析失败归宿：FR-02 只说「停留在缓冲区可重试」，未说回哪个状态；④ EX-12「导入中重启停留在中断前状态」与事务原子性矛盾——「入库中」未提交事务必被数据库回滚，不可能停留在「入库中」。 |
| 影响 | 前端状态展示、重试入口、批次列表过滤缺乏唯一事实源；测试用例无法对齐；「失败」与「待确认」并存时用户困惑。 |
| 修订建议 | 定稿以一张表统一收口，建议：已上传 → 待映射 → 待确认 → 入库中 → 已入库；解析失败 → 失败（记录 fail_reason，操作：重新解析/丢弃）；入库失败 → 回「待确认」（保留 fail_reason 与重试入口），**不进入「失败」**；「待上传」删除，或明确为前端本地草稿态、不落批次表（10.2 enum 同步）；EX-12 改为「入库中重启：未提交事务由数据库自动回滚，批次回『待确认』；解析中重启：停留在『已上传』」。 |

#### P1-2 异常清单缺口：6 类场景未覆盖

| 维度 | 内容 |
|------|------|
| 位置章节 | 12 章 EX-01~15 |
| 问题描述 | ① **上传阶段磁盘满/写失败**：FR-01 只覆盖「上传中断可重试」，半成品残留文件的清理规则缺失（缓冲区孤儿文件的又一来源）；② **并发/重复点击「确认入库」**（双击、多标签页）：9.2「入库中」仅说「锁定操作」，未定义重复提交行为（重复建事务？重复删文件？），单用户本机工具同样需要幂等；③ **恢复备份失败/恢复中断电**：FR-20 有预览与二次确认，但恢复动作若覆盖当前库后失败（备份文件损坏、磁盘满），原库已不可逆损坏，PRD 未要求「恢复前自动备份当前库」；④ **映射模板渠道冲突**：FR-03 模板按渠道保存，未定义同渠道再次保存时覆盖/另存/按文件名自动匹配的规则，及模板误匹配的纠正入口；⑤ **raw 跨月拆分写入失败**：事务保证整体回滚（技术安全），但产品层需明确「预检汇总与入库报告不一致时以入库报告为准」及批次内跨月失败的用户感知；⑥ **时间/金额解析失败记录与去重指纹的关系**：EX-06/07 把失败记录置待确认，但其指纹字段不完整，是否参与去重比对未定义——不参与则重复导入漏判，参与则可能误判。 |
| 影响 | 异常覆盖不全，实现期必然反复追问；③有数据不可逆损失风险；②⑤影响 M2 出口「回滚可验」的完整性。 |
| 修订建议 | 12 章新增 EX-16~EX-21（完整建议表见第三节）；其中③建议在 FR-20 增加规则「恢复执行前必须先对当前数据库做一次自动备份，恢复失败可回退」；⑥建议明确「指纹字段缺失的记录不参与自动去重，置待确认并提示人工核对」。 |

#### P1-3 FR-19「单条编辑」未定义可编辑字段范围及其与 raw 的关系

| 维度 | 内容 |
|------|------|
| 位置章节 | 7.3 FR-19；9.3（raw 只增不改）；10.2 |
| 问题描述 | FR-19 称明细支持「单条编辑」，但未定义哪些字段可改。若允许改交易时间/金额：主数据层改了而 raw 原貌不变（只增不改），两层同一条数据不一致；且 FR-08「按批次重算」会把主数据层冲回 raw 口径，用户的编辑丢失。若不允许改，PRD 应明示，否则用户预期「改时间」落空。 |
| 影响 | 数据一致性；重算与批次追溯的可靠性；用户预期管理。 |
| 修订建议 | 明确编辑范围：**分类、备注可改；交易时间/金额/方向/对方/商品说明等原始事实字段只读**（修正原始错误本期通过「重新导入正确文件」解决，不做冲正机制）；FR-19 业务规则写明该范围，FR-08 重算规则互相引用保证自洽。 |

#### P1-4 FR-08「按批次重算」未定义与人工修正的关系及失败中间态

| 维度 | 内容 |
|------|------|
| 位置章节 | 7.1 FR-08；9.4 |
| 问题描述 | 重算 = 用 raw 重新执行清洗与分类，但未定义：① 重算范围内已人工修正（corrected）/已排除（excluded）的记录是否被新规则覆盖——若覆盖，用户手工劳动静默丢失；② 重算事务中途失败时，主数据层是否残留「半新半旧」数据；③ FR-08 只说「提示影响范围」，具体展示什么（涉及多少条、其中多少条是人工修正过的）未定义。 |
| 影响 | 用户信任（改规则后手工修正被冲掉）；数据一致性；与 FR-11「历史重算」是同一机制，两处描述需一致。 |
| 修订建议 | FR-08 补充规则：① 重算默认**只处理未经人工修正/排除的记录**，人工处理记录保持原分类，报告中单列「N 条人工修正未重算」；② 重算为事务操作，失败整体回滚；③ 影响范围提示包含「将重算 N 条，其中人工修正 M 条（不重算）」。FR-11 引用同一规则。 |

#### P1-5 帮助/说明入口缺失：9.5 承诺「产品内明示口径」无功能承载

| 维度 | 内容 |
|------|------|
| 位置章节 | 9.5 vs 4.1 In Scope vs 第七章 FR-01~22 |
| 问题描述 | 9.5 要求资金流转口径「必须在产品『帮助/说明』中明示」，但 In Scope 与 FR 清单中**均无帮助/说明页功能**，该承诺在验收时无处落地。 |
| 影响 | 口径承诺落空；非技术用户遇到「钱花了报表却没记支出」时无自助解释，与 RK-05（分类错误累积）叠加侵蚀信任。 |
| 修订建议 | 新增 FR-23「帮助与说明（Must）」：静态页面，含资金流转口径说明（9.5 原文）、备份指引（呼应 FR-20 提醒）、导入三步引导；或明确挂靠 FR-22 设置页并将该部分升级 Must。成本极低，建议单列 FR 并在 RTM 补行。 |

#### P1-6 FR-08 优先级（Should）与 4.1 In Scope 承诺矛盾

| 维度 | 内容 |
|------|------|
| 位置章节 | 4.1 In Scope vs FR-08 |
| 问题描述 | 4.1 本期包含明确列出「从原始库重算主数据层」，FR-08 却标 Should；按第七章约定 Should 非必须，范围声明与优先级自相矛盾。 |

## 四、遗留问题处置建议

### Q-02（理财是否放到后续版本）——建议直接收口，不阻塞研发

- **处置结论**：可依据 PRD 自身内容推定收口。4.2 Out of Scope 已明确「理财收益记录、资产配置、投资建议」本期不做（原因：用户处于「先看清现状」阶段，避免范围蔓延）；5.3 演进路径已将「理财收益记录与资产总览」放入后续 v1.3 并给出触发条件（用户形成稳定结余并明确提出）。两者共同构成完整的范围决策链，Q-02 的答案已被文档自身推定。
- **落地动作**：v2.0 将 14.2 的 Q-02 状态改为「已推定收口（依据 4.2/5.3），待用户最终确认后关闭」；M1–M4 内容均不涉及理财，**不阻塞研发启动**；用户确认后从遗留清单移除。
- **连带修订**：帮助/说明页（P1-5 新增 FR-23）中无需包含理财内容，与本处置保持一致。

### Q-01（账单格式与脱敏样例）——建议保留为阻塞依赖，明确 fallback 与排期弹性

- **保留理由**：样例文件直接决定字段映射精确度与默认规则包质量，是 13.2 已标注的阻塞项，M1 出口标准「一份真实账单可上传、解析、映射、预检」依赖它。
- **Fallback（用户不立即响应也能启动）**：
  1. M1 以「通用表头自动识别 + 手动映射 + 渠道模板保存」交付——FR-03 的模板机制本身就是为格式未知设计的兜底；
  2. 默认规则包以保守关键词集交付（覆盖主流平台常见对方名），自动识别率目标降为「可用」，其余记录进待确认队列（FR-12）；
  3. 样例就绪窗口设在 M1–M2 之间：就绪则补充精确模板与规则，**不改架构、不返工**；M2 启动时仍未就绪，M3「分类引擎」出口标准中的「默认规则包可用」降级为「规则引擎 + 保守包可用」。
- **排期风险与缓冲**：M1 出口标准措辞建议弹性化为「一份真实账单（脱敏）或构造样例可完成上传、解析、映射、预检」；另建议在 M1 期间向用户提供「手机端导出指引」自助促成样例（A-01 假设用户能导出 CSV，成立概率高）。
- **需求侧判断**：Q-01 不构成「需求不清」，只构成「精确度未知」，fallback 已覆盖，不应阻塞整体排期。

## 五、架构原则落点建议

用户提出的 4 条架构原则（前后端分离分层、接口依赖 + 类型检测/数据校验、内部信任不重复防御、可扩展可复用）总体与 PRD 无冲突，但 PRD 目前**缺少承载这些原则的章节**，且其中「内部信任接口」存在被误读为「信任前端输入」的风险，必须在需求侧写清信任边界。

### 5.1 建议新增位置

推荐在**第八章「非功能需求」新增小节「架构设计原则与系统分层（需求侧约束）」**（备选：第五章新增 5.4；推荐第八章——属约束性质而非选型论证，且与现有「架构」行相邻）。同时在 NFR 表增加「可扩展性」一行。**详细分层设计、模块划分、技术选型由架构师在技术方案中产出，本 PRD 只定原则与边界，不写框架细节**（5.3 末尾「技术栈为建议而非需求」的定位保持不变）。

### 5.2 PRD 级表述建议（框架性，需求语言）

1. **分层职责**：系统分「展示层（前端 SPA）/ 接口层（REST API）/ 业务层（导入、分类、统计、备份）/ 数据层（缓冲区文件、SQLite）」，一层一类业务；**展示层不含统计计算**（保证 FR-16/FR-19 口径一致，统计为单一计算源），业务层不含展示决策。
2. **接口契约**：模块间经定义良好的接口交互，接口须声明数据契约（字段类型、取值范围、必填性），契约变更可追溯。
3. **信任边界（须显式写出，防止误读）**：前端输入（上传文件、接口参数）**一律视为不可信**，必须在系统入口一次性完成校验（文件格式/大小/编码、字段映射合法性、金额/时间合法性、恢复操作二次确认）；**内部模块间信任已通过契约校验的数据，不重复校验**。即原则中的「信任」指后端模块之间，不指跨进程的前端→后端边界。
4. **可扩展与可复用**：分类规则、映射模板、报表周期、系统设置为可配置扩展点；REST API 按资源化设计，为 5.3「可选加密云同步」预留复用；**新增报表周期不得复制统计逻辑，必须复用 10.3 统一口径实现**（口径表为唯一口径源）。

### 5.3 与现有需求的一致性检查

- 原则 1 与 FR-13/FR-16/FR-19 的「同口径」验收互补，建议顺带在 10.3 或 NFR 明确「统计计算仅在后端完成」；
- 原则 3 与 FR-02「禁止解析失败写库」、FR-04「预检只读」一致，属入口校验的具体化；与第十一章安全要求（RK-01 仅监听 127.0.0.1）方向一致，并堵住「以内部信任为由跳过前端输入校验」的误读风险；
- 原则 4 与 5.3 演进路径、FR-11/FR-22 的可配置设计一致；
- **无冲突**；上述表述均为需求/约束语言，不涉及具体框架与选型。
